## Identity and request authority

Supabase validates session identity; server uses verified `getUser()`/equivalent provider-validated claims for the configured project. Cookie parsing or `getSession()` alone never establishes trusted subject. Current repo already calls getUser for home/session refresh, but does not resolve application role/status. The proposed backend resolves `accounts.id = verified subject`, rejects missing/PENDING/DISABLED account and verifies business role before domain queries. Provider verification/recovery remains separate from business activation. Server credentials and user cookie cannot be interchanged into one Supabase client that accidentally changes authorization context. [Supabase SSR guidance](https://supabase.com/docs/guides/auth/server-side/creating-a-client?queryGroups=framework&framework=nextjs) describes validated server authentication; installed SDK behavior must be tested under the later implementation scope.

Role is a fixed DB scalar ADMIN/TEACHER/LEARNER, not raw user metadata, client JSON, role array or a stale authorization JWT claim. Profile edits allow display name, locale, native language, timezone and own avatar reference only. Account status/role and all learner evidence fields are excluded. Staff uses a separate Learner account to learn. Protected requests recheck current account on every invocation; middleware navigation redirects are UX, not the authorization boundary. Disable with still-valid Auth token must deny the next protected query/command/media stream. In-flight operations use documented row locks; no global immediate revocation claim.

The runtime arrangement below is PROPOSED, not a verified property of the current Prisma connection or any live database. The proposed ordinary Prisma login is the dedicated `lingora_runtime` non-owner, non-superuser, NOBYPASSRLS runtime role. A separately isolated Supabase service-role adapter may bypass RLS for provider operations; it still must authorize the verified actor, exact assignment/object and command before every call. If an eventual domain connection bypasses RLS, server authorization through command checks and safe DTO projection remains mandatory; RLS never supplies business authorization by itself. No actual role flags, grants, schema exposure or FORCE RLS state were inspected here.

## Database principals and exposure

| Principal | Connection/source | Proposed privileges | Boundary |
|---|---|---|---|
| Browser/public Auth client | public Supabase Auth key and own session | Auth operations only; no application-table grants | No grading/admin/data mutation |
| `anon`, `authenticated` Data API roles | Supabase API | No USAGE/table/function privileges on app/app_private | Both schemas unexposed; explicit default-grant revocation |
| `lingora_runtime` | Next.js server-only Prisma connection | Non-owner/NOBYPASSRLS; SELECT and narrowly granted writes/functions | No CREATE/ALTER/DROP/TRUNCATE, role management, published payload changes or evidence deletion |
| `lingora_migrator`/object owner | separately approved operator/tool | DDL/security provisioning | Credential absent from app deployments |
| Supabase service-role adapter | server-only isolated Auth/Storage adapter | Provider identity invite/storage tasks | RLS bypass acknowledged; authorize validated actor/assignment before call |
| Audit append function owner | restricted non-login owner | Append audit and read minimum account authorization | No arbitrary domain mutation; runtime EXECUTE only |

All application tables ENABLE and FORCE RLS for the runtime principal, including private tables. FORCE does not stop superusers/BYPASSRLS principals; therefore do not use provider service role/owner for ordinary Prisma queries. Schema isolation reduces Data API exposure; RLS adds ownership/role protection for the actual DB role. RLS cannot hide columns from a row SELECT, so grading keys and private responses have physical separation and explicit safe projections. [Supabase RLS documentation](https://supabase.com/docs/guides/database/postgres/row-level-security) explains grants, policy filtering and bypass behavior; these are separate controls, not automatic Prisma behavior.

Use a parameterized transaction-local subject set only by verified server wrapper; all subsequent Prisma operations use its transaction client. No pooled session-global user variables. Any missing/invalid UUID context fails closed. A custom GUC is not proof against a compromised runtime DB credential; the server is trusted to set it. This is an explicit trust boundary, not an unforgeable DB identity claim.

Account lookup policy avoids recursive self-query: a narrow security-definer helper reads `accounts` by transaction subject and returns only active role/subject needed for policies; FORCE RLS still applies to helper owners. Use a dedicated non-login/NOBYPASSRLS `lingora_authz_reader` function principal with SELECT on only account id/role/status and a principal-specific nonrecursive SELECT policy allowing that lookup. This principal is not the table owner and never exposed as a callable arbitrary-account query. Pin empty search_path, fully qualify all relations/functions and revoke PUBLIC EXECUTE. Helpers reject missing subject and status. Runtime has no membership/SET ROLE entitlement for helper principals; possession of the runtime login cannot assume them. Minimum Admin support query returns permitted identity/status/role plus context language/status/selected course summary; does not grant blanket Admin SELECT on learner attempts/results/SRS/history. Auth email lookup is through the controlled adapter for specified account IDs/search only.

### Principals for narrow functions under FORCE RLS

All helper principals below are non-login, non-superuser and NOBYPASSRLS; none relies on table ownership for a bypass. Each has only explicitly required column/table grants and a principal-specific policy. Runtime is not a member and cannot SET ROLE. Function EXECUTE grants are individually enumerated, PUBLIC/anon/authenticated revoked, empty search_path pinned, no dynamic SQL. Definer functions validate the caller-derived transaction subject and independently authorize the exact command before privileged internal access.

- `lingora_authz_reader`: SELECT only accounts.id/role/status; nonrecursive principal SELECT policy; returns the subject's status/role only. Used by ordinary runtime policies. It cannot create/update accounts or read evidence/secrets.
- `lingora_grader`: SELECT private grading data and required pinned prompt/membership/own attempt inputs via explicit principal read policies; bounded functions verify ACTIVE LEARNER and matching owned context/content scope. Direct role login/assumption is unavailable. Internal grading helpers return bounded outcomes only to checked finalizer/authoring functions; no runtime EXECUTE on helpers returning raw key/rubric or private item outcomes. Authorized Admin key review uses its separate read-only review function.
- `lingora_learner_writer`: `learning_contexts SELECT` for the authenticated owner supports lookup/resume, plus required pinned membership, open attempts, own evidence and cards; INSERT contexts, attempts/responses/completions, cards/review operations, assessment attempts/private responses/results and receipts; narrow UPDATE on open attempts/context/card schedule. The first-context command does not require a context row in its authorization predicate: validate ACTIVE learner, learnable language and configured course, then take actor/course locks and enforce max-two ACTIVE before insert. Existing-context reads are explicitly granted by owner RLS. Every function rechecks ownership, scope, queue/gates/config, operation hash and row versions. Completed evidence UPDATE/DELETE is denied.
- `lingora_content_writer`: SELECT minimum authoring-parent id/assignment/state/row_version and item ownership; UPDATE only parent updated_at/row_version; SELECT(item_revision_id,grading_data,feedback_data,schema_version) plus INSERT/UPDATE private grading secrets for the current assigned Teacher on an editable authoring owner. It has table-level DELETE only on lesson_exercises, lesson_vocabulary_links, media_bindings and assessment_version_items, exercised solely inside remove_draft_member. Principal RLS limits those deletes to an exact association whose current assigned parent is DRAFT/CHANGES_REQUESTED. The function locks parent/assignment, checks expected version and readiness impact, increments parent version, and cannot delete item identities/revisions/assets/evidence or frozen rows. Runtime has EXECUTE on this checked function, no generic table DELETE.
- `lingora_transition_writer`: column-scoped lifecycle/status/pointer updates and provenance/receipt inserts. It exposes submit_assigned_work as a separately checked Teacher capability: current ACTIVE assignee, exact target, editable state, readiness/media/tag validation, expected row_version and current assignment generation are required; it can only move the package to IN_REVIEW and append SUBMIT provenance/audit. Separate Admin-only functions request changes, approve, publish, archive/withdraw or disable/reenable; approval/publication compare the pinned generation/snapshot. No generic runtime lifecycle UPDATE is granted, and no authored payload/grading or historical evidence UPDATE/DELETE is allowed.
- `lingora_audit_writer`: INSERT only sanitized audit columns, explicit principal INSERT policy; no UPDATE/DELETE. A check constraint distinguishes ACCOUNT (account FK), VERIFIED_AUTH_SUBJECT (verified subject UUID with no account FK), and SYSTEM (no actor fields). The missing-account denial path accepts only the provider-verified subject supplied by the trusted wrapper; it never creates an account or records credentials. Independent denied-action append checks correlation/actor kind and finite safe context. Admin audit SELECT is a separate runtime policy/DTO.
- `lingora_scoped_locker`: non-login/NOBYPASSRLS principal with minimum SELECT and lock-only column UPDATE privilege on accounts, courses, blueprints, assignments, lessons, revisions, assessment versions and media_assets; additionally SELECT(id,learner_id,language_id,course_id,status) on learning_contexts and SELECT(id,is_learnable) on languages for its independently checked context/config lookup. It runs fixed fully qualified SELECT FOR UPDATE statements only; no UPDATE, arbitrary table name, dynamic SQL or role assumption. Actor lock is the verified ACTIVE subject. Existing-context course lock requires an owned matching context. The separate FIRST_CONTEXT_CREATE branch validates the ACTIVE Learner, learnable language and server-resolved course/config but deliberately has no existing-context predicate. Teacher locks rederive current assignment/target; Admin locks require a permitted command. Media locks check retirement state. Callers recheck authorization after acquiring locks. Runtime receives only specific EXECUTE, never membership in this role.
- `lingora_auth_provisioner`: SELECT minimum accounts.id/role/status and Auth UUID/email/server-controlled correlation marker (no password/token/credential columns); INSERT accounts; column UPDATE accounts.status/activated_at/updated_at/row_version only for verified PENDING activation; SELECT/INSERT/UPDATE private provisioning_requests operation/email/UUID/state/correlation/error fields. Explicit principal policies permit these internal operations under FORCE RLS. Runtime EXECUTE only checked Admin Teacher-provision/reservation/reconcile commands and subject-bound activation; no public generic INSERT or private-marker setter. The Auth trigger function is executable only by its installed trigger/provider owner, not as a runtime RPC. Provider admin API adapter alone writes the trusted private marker and supplies exact returned UUID; reconciliation independently reads that marker via controlled adapter and compares private operation reservation, never client user metadata or email alone. Functions require ACTIVE ADMIN for Teacher reservation/reconcile or exact authenticated PENDING subject plus verified provider activation; controlled ADMIN bootstrap is executable only by separately approved operator. Accounts.role remains fixed after insertion. Unmatched or publicly created identity fails closed and needs operator resolution.

PostgreSQL SELECT FOR UPDATE/SHARE requires UPDATE privilege on at least one locked-table column. For create/resume/pause, `lingora_learner_writer` itself locks the stable account row with the explicit privileges below, then delegates course serialization to `lingora_scoped_locker`; other scoped locks retain their existing owner. Context reads/writes use `lingora_learner_writer`. This preserves the distinction between lock permission and domain mutation. No function assumes its owner bypasses FORCE RLS. [PostgreSQL 15 SELECT documentation](https://www.postgresql.org/docs/15/sql-select.html) specifies the lock privilege requirement.

These principal-specific policies deliberately grant internal rows/columns needed by functions; they do not make the functions safe by themselves. Safe function arguments/authorization/projection and grants are required and independently tested. No blanket BYPASSRLS, and FORCE RLS tests cover every definer path. Trigger owners executing Auth lifecycle cannot trust a client-selected DB subject.

## Proposed policy/function implementation responsibilities

- Active-subject helper: trusted GUC UUID → account row → ACTIVE role. Independent helper for own safe profile/activation of PENDING is tightly scoped; cannot open learner/staff domain operations.
- Own learner evidence policies: join context.learner_id or card.learner_id to subject; account LEARNER/ACTIVE. SRS does not require context ACTIVE; lesson/assessment mutations do. History reads remain available for PAUSED contexts.
- Teacher policies: actor TEACHER/ACTIVE and content assignment.current_teacher_id=subject; joined owner package DRAFT/CHANGES_REQUESTED for I/U; child write locks and checks parent version. Administrative review policy does not grant content U.
- Admin policies: only curriculum/blueprint/assignment configuration writes, status/lifecycle operations and audit/support reads described above; no learner-evidence read beyond minimal support or evidence mutation. No global `is_admin() OR true` bypass.
- Private grader functions: validate own actor/context/attempt and pinned membership, read secret internally, return practice feedback or assessment aggregate only. Secret authoring read/write path independently checks assigned Teacher/editable parent; Admin secret review read only.
- Immutability triggers: guard payload, secret, membership, snapshots, pinned FK, responses/results/completions/reviews/audit. Lifecycle metadata changes only within named checked transition functions: assigned ACTIVE Teacher SUBMIT may set IN_REVIEW/submitted actor/time/version/scope pin, while approval/publication/withdrawal and other lifecycle changes remain Admin-only; they cannot unfreeze old item bytes or change actor history.
- Provider auth trigger: safe self-registration only; staff reservation suppresses generic profile creation until exact controlled identity is reconciled. Trigger and function owners/grants/search paths recorded in future migration tests.
- RLS for unexposed private tables is not a replacement for narrow grants. Grading function ownership and runtime EXECUTE privileges must be reviewed against every callable path. PUBLIC, anon, authenticated EXECUTE revoked; no arbitrary SECURITY DEFINER dynamic SQL.

## Media and delete policies

Both content and avatar buckets are private. Preserve current bucket naming/limits as baseline: avatars 5 MiB, audio 10 MiB. Additional media formats need explicit configuration/test approval; do not silently make bucket public. Content owner is assignment and binding revision, not uploader-only entitlement. Reassignment removes prior Teacher's new upload/preview authority; immutable published learner stream remains available when authorized.

Learner cannot turn an asset UUID into a public URL. Content streaming resolves binding and authorized published lesson or own pinned assessment attempt. Audio serving rechecks status on each request including range requests. Short-lived signed URLs have residual validity; sensitive assessment/lesson bytes use server-authorized streaming where next-request disable is required. Provider key stays server-side.

Generic domain D is denied. Only remove_draft_member can delete an association row inside the editable Teacher package; this does not delete referenced content/item/asset or any evidence. Published media/assets/history are retained. MEDIA_CLEANUP reserves an unreferenced asset under its row lock, blocks future references via retired_at, performs a final DB check, then calls provider deletion outside the transaction. A retry retains the tombstone. No FK cascades to evidence. Account disable, content withdrawal/archive and context pause never imply history deletion.
