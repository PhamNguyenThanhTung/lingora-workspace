## Identity and request authority

Supabase validates session identity; server uses verified `getUser()`/equivalent provider-validated claims for the configured project. Cookie parsing or `getSession()` alone never establishes trusted subject. Current repo already calls getUser for home/session refresh, but does not resolve application role/status. The proposed backend resolves `accounts.id = verified subject`, rejects missing/PENDING/DISABLED account and verifies business role before domain queries. Provider verification/recovery remains separate from business activation. Server credentials and user cookie cannot be interchanged into one Supabase client that accidentally changes authorization context. [Supabase SSR guidance](https://supabase.com/docs/guides/auth/server-side/creating-a-client?queryGroups=framework&framework=nextjs) describes validated server authentication; installed SDK behavior must be tested under the later implementation scope.

Role is a fixed DB scalar ADMIN/TEACHER/LEARNER, not raw user metadata, client JSON, role array or a stale authorization JWT claim. Profile edits allow display name, locale, native language, timezone and own avatar reference only. Account status/role and all learner evidence fields are excluded. Staff uses a separate Learner account to learn. Protected requests recheck current account on every invocation; middleware navigation redirects are UX, not the authorization boundary. Disable with still-valid Auth token must deny the next protected query/command/media stream. In-flight operations use documented row locks; no global immediate revocation claim.

The runtime arrangement below is PROPOSED, not a verified property of the current Prisma connection or any live database. The proposed ordinary Prisma login is the dedicated `lingora_runtime` non-owner, non-superuser, NOBYPASSRLS runtime role. A separately isolated Supabase service-role adapter may bypass RLS for provider operations; it still must authorize the verified actor, exact assignment/object and command before every call. If an eventual domain connection bypasses RLS, server authorization through command checks and safe DTO projection remains mandatory; RLS never supplies business authorization by itself. No actual role flags, grants, schema exposure or FORCE RLS state were inspected here.

## Database principals and exposure

| Principal | Connection/source | Proposed privileges | Boundary |
|---|---|---|---|
| Browser/public Auth client | public Supabase Auth key and own session | Auth operations only; no application-table grants | No grading/admin/data mutation |
| `anon`, `authenticated` Data API roles | Supabase API | No USAGE/table/function privileges on app/app_private | Both schemas unexposed; explicit default-grant revocation |
| `lingora_runtime` | Next.js server-only Prisma connection | Non-owner/NOBYPASSRLS; SELECT and narrowly granted writes/functions | No CREATE/ALTER/DROP/TRUNCATE, role management, published payload changes or evidence deletion |
| `lingora_migrator`/object owner | separately approved operator/tool | DDL/security provisioning | Credential absent from app deployments |
| Supabase service-role adapter | server-only isolated Auth/Storage adapter | Provider identity invite/storage tasks | RLS bypass acknowledged; authorize validated actor/assignment before call |
| Audit append function owner | restricted non-login owner | Append audit and read minimum account authorization | No arbitrary domain mutation; runtime EXECUTE only |

All application tables ENABLE and FORCE RLS for the runtime principal, including private tables. FORCE does not stop superusers/BYPASSRLS principals; therefore do not use provider service role/owner for ordinary Prisma queries. Schema isolation reduces Data API exposure; RLS adds ownership/role protection for the actual DB role. RLS cannot hide columns from a row SELECT, so grading keys and private responses have physical separation and explicit safe projections. [Supabase RLS documentation](https://supabase.com/docs/guides/database/postgres/row-level-security) explains grants, policy filtering and bypass behavior; these are separate controls, not automatic Prisma behavior.

Use a parameterized transaction-local subject set only by verified server wrapper; all subsequent Prisma operations use its transaction client. No pooled session-global user variables. Any missing/invalid UUID context fails closed. A custom GUC is not proof against a compromised runtime DB credential; the server is trusted to set it. This is an explicit trust boundary, not an unforgeable DB identity claim.

Account lookup policy avoids recursive self-query: a narrow security-definer helper reads `accounts` by transaction subject and returns only active role/subject needed for policies; FORCE RLS still applies to helper owners. Use a dedicated non-login/NOBYPASSRLS `lingora_authz_reader` function principal with SELECT on only account id/role/status and a principal-specific nonrecursive SELECT policy allowing that lookup. This principal is not the table owner and never exposed as a callable arbitrary-account query. Pin empty search_path, fully qualify all relations/functions and revoke PUBLIC EXECUTE. Helpers reject missing subject and status. Runtime has no membership/SET ROLE entitlement for helper principals; possession of the runtime login cannot assume them. Minimum Admin support query returns permitted identity/status/role plus context language/status/selected course summary; does not grant blanket Admin SELECT on learner attempts/results/SRS/history. Auth email lookup is through the controlled adapter for specified account IDs/search only.

### FTR-02/03 execution addendum — 2026-10-22

The official disposition and implementation spec §4–6 select Auth API/recovery, lock-only policies and **LOCK-01**, the only lock-order authority. Actor/target account rows lock together in sorted UUID order, not actor→target request order; domain parents follow the total rank in that spec. Lock-only principals require scoped SELECT USING **and** UPDATE USING on frozen as well as editable rows, column UPDATE grant and WITH CHECK(false) for actual writes. Genuine writer policies stay separate. Use FOR NO KEY UPDATE for stable parent serialization to coexist with FK KEY SHARE checks; no late upgrade. Short command traces below are subsequences; none permits inverse ordering or omits policy checks. These are selected contracts, not executed SQL/RLS evidence; A1/A2/A3 remain mandatory disposable gates.

### Principals for narrow functions under FORCE RLS

All helper principals below are non-login, non-superuser and NOBYPASSRLS; none relies on table ownership for a bypass. Each has only explicitly required column/table grants and a principal-specific policy. Runtime is not a member and cannot SET ROLE. Function EXECUTE grants are individually enumerated, PUBLIC/anon/authenticated revoked, empty search_path pinned, no dynamic SQL. Definer functions validate the caller-derived transaction subject and independently authorize the exact command before privileged internal access.

- `lingora_authz_reader`: SELECT only accounts.id/role/status; nonrecursive principal SELECT policy; returns the subject's status/role only. It cannot create/update accounts or read content/evidence/secrets.
- `lingora_fingerprint_reader`: dedicated non-login/NOBYPASSRLS, non-owner principal; no role membership or direct runtime access. It owns only the fixed existence checker and has column SELECT on `item_identities(id,practice_exposed_at)`, `item_revisions(id,item_id,exact_fingerprint)`, `lesson_exercises(lesson_revision_id,item_revision_id)`, `lesson_revisions(id,status)`, `assessment_version_items(assessment_version_id,item_revision_id)`, and `assessment_versions(id,status,is_active)`. Principal-specific FORCE RLS policies expose only published practice memberships, exposed practice identities, and active published assessment memberships plus their exact item revision hashes. It cannot read prompts, grading secrets, accounts, or mutate rows.
- `lingora_grader`: SELECT private grading data and required pinned prompt/membership/own attempt inputs via explicit principal read policies; bounded functions verify ACTIVE LEARNER and matching owned context/content scope. Direct role login/assumption is unavailable. Internal grading helpers return bounded outcomes only to checked finalizer/authoring functions; no runtime EXECUTE on helpers returning raw key/rubric or private item outcomes. Authorized Admin key review uses its separate read-only review function.
- `lingora_learner_writer`: `learning_contexts SELECT` for the authenticated owner supports lookup/resume, plus required pinned membership, open attempts, own evidence and cards; INSERT contexts, attempts/responses/completions, cards/review operations, assessment attempts/private responses/results and receipts; narrow UPDATE on open attempts/context/card schedule. The first-context command does not require a context row in its authorization predicate: validate ACTIVE learner, learnable language and configured course, then take actor/course locks and enforce max-two ACTIVE before insert. Existing-context reads are explicitly granted by owner RLS. Every function rechecks ownership, scope, queue/gates/config, operation hash and row versions. Completed evidence UPDATE/DELETE is denied.
- `lingora_content_writer`: SELECT exact Lesson authoring owner/assignment/episode/state/row_version and scoped items/catalog/media; INSERT/UPDATE unfrozen Lesson payload/items/keys, including `item_revisions.is_draft_omitted` through the desired-state setter with an expected parent version; parent updated_at/row_version UPDATE. DELETE only lesson_exercises, lesson_vocabulary_links and media_bindings inside remove_draft_member for a current assigned unfrozen editable Lesson. No assessment_versions or assessment_version_items I/U/D. Exact grants/functions and independent principal policies are below.
- `lingora_transition_writer`: narrow Lesson Teacher SUBMIT lifecycle/provenance/receipt writes, plus separate Admin-only review/approve/publish/archive/withdraw and account status paths. Teacher submit verifies current Lesson assignee, episode/scope, unfrozen editable state, readiness and row_version; freezes source bytes. Admin review of assembled versions compares blueprint and all source requirement pins. No composition/payload/key or historical evidence edits.
- `lingora_audit_writer`: INSERT only sanitized audit columns, explicit principal INSERT policy; no UPDATE/DELETE. A check constraint distinguishes ACCOUNT (account FK), VERIFIED_AUTH_SUBJECT (verified subject UUID with no account FK), and SYSTEM (no actor fields). The missing-account denial path accepts only the provider-verified subject supplied by the trusted wrapper; it never creates an account or records credentials. Independent denied-action append checks correlation/actor kind and finite safe context. Admin audit SELECT is a separate runtime policy/DTO.
- `lingora_scoped_locker`: non-login/NOBYPASSRLS principal with minimum SELECT and lock-only column UPDATE privilege on accounts, courses, blueprints, assignments, lessons, revisions, assessment versions and media_assets; additionally SELECT(id,learner_id,language_id,course_id,status) on learning_contexts and SELECT(id,is_learnable) on languages for its independently checked context/config lookup. It runs fixed fully qualified ordered SELECT FOR NO KEY UPDATE statements only (LOCK-01); no UPDATE, arbitrary table name, dynamic SQL or role assumption. Actor lock is the verified ACTIVE subject. Existing-context course lock requires an owned matching context. The separate FIRST_CONTEXT_CREATE branch validates the ACTIVE Learner, learnable language and server-resolved course/config but deliberately has no existing-context predicate. Teacher locks rederive current assignment/target; Admin locks require a permitted command. Media locks check retirement state. Callers recheck authorization after acquiring locks. Runtime receives only specific EXECUTE, never membership in this role.
- `lingora_auth_provisioner`: SELECT minimum accounts.id/role/status and Auth UUID/email/server-controlled correlation marker (no password/token/credential columns); INSERT accounts; column UPDATE accounts.status/activated_at/updated_at/row_version only for verified PENDING activation; SELECT/INSERT/UPDATE private provisioning_requests operation/email/UUID/state/correlation/error fields. Explicit principal policies permit these operations under FORCE RLS. Ordinary runtime EXECUTE is limited to checked ACTIVE-Admin Teacher reservation/safe operation status; **bind/reconcile/activation requires the isolated Auth-adapter login**, and ADMIN bootstrap the controlled operator. No public generic INSERT, activation or marker setter. The Auth trigger is callable only by its installed provider trigger path. The adapter creates a pre-reserved server UUID + private marker using createUser, verifies exact getUserById correspondence, binds PENDING, then invites that same existing unconfirmed UUID. Provider calls stay outside DB transactions. Verified password-setup success precedes subject-bound PENDING activation; no browser flag/email-only proof, and DISABLED never activates. Accounts.role remains fixed; unmatched/public identity fails closed. See spec §4 and mandatory A1 recovery/trigger tests.

PostgreSQL SELECT FOR UPDATE/SHARE requires UPDATE privilege on at least one locked-table column. For create/resume/pause, `lingora_learner_writer` itself locks the stable account row with the explicit privileges below, then delegates course serialization to `lingora_scoped_locker`; other scoped locks retain their existing owner. Context reads/writes use `lingora_learner_writer`. This preserves the distinction between lock permission and domain mutation. No function assumes its owner bypasses FORCE RLS. [PostgreSQL 15 SELECT documentation](https://www.postgresql.org/docs/15/sql-select.html) specifies the lock privilege requirement.

These principal-specific policies deliberately grant internal rows/columns needed by functions; they do not make the functions safe by themselves. Safe function arguments/authorization/projection and grants are required and independently tested. No blanket BYPASSRLS, and FORCE RLS tests cover every definer path. Trigger owners executing Auth lifecycle cannot trust a client-selected DB subject.

## Proposed policy/function implementation responsibilities

- Active-subject helper: trusted GUC UUID → account row → ACTIVE role. Independent helper for own safe profile/activation of PENDING is tightly scoped; cannot open learner/staff domain operations.
- Own learner evidence policies: join context.learner_id or card.learner_id to subject; account LEARNER/ACTIVE. SRS does not require context ACTIVE; lesson/assessment mutations do. History reads remain available for PAUSED contexts.
- Teacher policies: ACTIVE TEACHER + current Lesson assignee; source edits require unfrozen editable Lesson/item owner and expected parent version. Submitted own source/status/feedback projection is read-only and restricted to current assignment. No complete assembled exam/key read via source membership. No assessment version/member writes.
- Admin policies: only curriculum/blueprint/assignment configuration writes, status/lifecycle operations and audit/support reads described above; no learner-evidence read beyond minimal support or evidence mutation. No global `is_admin() OR true` bypass.
- Private grader functions: validate own actor/context/attempt and pinned membership, read secret internally, return practice feedback or assessment aggregate only. Secret authoring read/write path independently checks assigned Teacher/editable parent; Admin secret review read only.
- Immutability triggers: submitted source payload/items/keys/bindings and assembled version payload/members remain frozen, even after CHANGES_REQUESTED. Only named lifecycle fields may change via Teacher Lesson SUBMIT or Admin transitions; corrections create successors. Creator/creation episode, source submit/episode pins, attempts/results/reviews/audit never change.
- Provider auth trigger: safe self-registration only; staff reservation suppresses generic profile creation until exact controlled identity is reconciled. Trigger and function owners/grants/search paths recorded in future migration tests.
- RLS for unexposed private tables is not a replacement for narrow grants. Grading function ownership and runtime EXECUTE privileges must be reviewed against every callable path. PUBLIC, anon, authenticated EXECUTE revoked; no arbitrary SECURITY DEFINER dynamic SQL.

## Media and delete policies

Both content and avatar buckets are private. Preserve current bucket naming/limits as baseline: avatars 5 MiB, audio 10 MiB. Additional media formats need explicit configuration/test approval; do not silently make bucket public. Content owner is assignment and binding revision, not uploader-only entitlement. Reassignment removes prior Teacher's new upload/preview authority; immutable published learner stream remains available when authorized.

Learner cannot turn an asset UUID into a public URL. Content streaming resolves binding and authorized published lesson or own pinned assessment attempt. Audio serving rechecks status on each request including range requests. Short-lived signed URLs have residual validity; sensitive assessment/lesson bytes use server-authorized streaming where next-request disable is required. Provider key stays server-side.

Generic domain D is denied. Only remove_draft_member can delete an association row inside the editable Teacher package; this does not delete referenced content/item/asset or any evidence. Published media/assets/history are retained. MEDIA_CLEANUP reserves an unreferenced asset under its row lock, blocks future references via retired_at, performs a final DB check, then calls provider deletion outside the transaction. A retry retains the tombstone. No FK cascades to evidence. Account disable, content withdrawal/archive and context pause never imply history deletion.

## RDR-03 — Cross-scope fingerprint collision checker privileges and locking trace

`app_private.check_fingerprint_collision(p_fingerprint text, p_check_direction text)` is owned by the dedicated non-login `lingora_fingerprint_reader` principal, `SECURITY DEFINER`, `SET search_path = ''`, and fully qualified relation names. It validates nonempty input and the exact direction (`PRACTICE` or `ASSESSMENT`), executes fixed `EXISTS` queries under FORCE RLS, and returns one boolean. It never returns a fingerprint, item ID, prompt, option, key, or membership metadata.

The query uses these exact read sets:

| Direction | Checked publication action | Fixed existence query | Read columns |
|---|---|---|---|
| `PRACTICE` | Admin publishes an ASSESSMENT version; check for practice collision | `EXISTS (lesson_exercises le JOIN lesson_revisions lr ON lr.id=le.lesson_revision_id AND lr.status='PUBLISHED' JOIN item_revisions ir ON ir.id=le.item_revision_id WHERE ir.exact_fingerprint=p_fingerprint) OR EXISTS (item_identities ii JOIN item_revisions ir ON ir.item_id=ii.id WHERE ir.exact_fingerprint=p_fingerprint AND ii.practice_exposed_at IS NOT NULL)` | `lesson_exercises(lesson_revision_id,item_revision_id)`; `lesson_revisions(id,status)`; `item_revisions(id,item_id,exact_fingerprint)`; `item_identities(id,practice_exposed_at)` |
| `ASSESSMENT` | Admin publishes or exposes a PRACTICE Lesson; check for assessment collision | `EXISTS (assessment_version_items avi JOIN assessment_versions av ON av.id=avi.assessment_version_id AND av.status='PUBLISHED' AND av.is_active JOIN item_revisions ir ON ir.id=avi.item_revision_id WHERE ir.exact_fingerprint=p_fingerprint)` | `assessment_version_items(assessment_version_id,item_revision_id)`; `assessment_versions(id,status,is_active)`; `item_revisions(id,exact_fingerprint)` |

The `lingora_fingerprint_reader` principal has SELECT only on those listed columns and no INSERT/UPDATE/DELETE, login, membership, BYPASSRLS, account read, prompt access, or grading-secret access. Its independent FORCE RLS policies are:

| Policy | Relation | Predicate |
|---|---|---|
| `fp_identity_exposed` | `app.item_identities` | `practice_exposed_at IS NOT NULL` |
| `fp_lesson_published` | `app.lesson_revisions` | `status = 'PUBLISHED'` |
| `fp_lesson_membership_published` | `app.lesson_exercises` | `EXISTS (SELECT 1 FROM app.lesson_revisions lr WHERE lr.id = lesson_revision_id AND lr.status = 'PUBLISHED')` |
| `fp_assessment_version_active` | `app.assessment_versions` | `status = 'PUBLISHED' AND is_active` |
| `fp_assessment_membership_active` | `app.assessment_version_items` | `EXISTS (SELECT 1 FROM app.assessment_versions av WHERE av.id = assessment_version_id AND av.status = 'PUBLISHED' AND av.is_active)` |
| `fp_revision_hash_referenced` | `app.item_revisions` | `EXISTS` in a visible `lesson_exercises` or `assessment_version_items` row for this `id`, or in an `item_identities` row for this `item_id` with recorded practice exposure |

The membership policies depend only on parent lifecycle rows; those parent policies do not query memberships, so the predicates do not recurse. These policies do not depend on `authz_reader`, `grader`, `content_writer`, or caller grants. FORCE RLS remains enabled on each source relation. Application principals cannot SET ROLE to the checker principal.

Only `lingora_transition_writer` receives EXECUTE on the checker, and only its checked Admin publication functions call it. The checked function validates the active Admin, exact target, approval and row version before the internal call. `content_writer`, assembly service, learner_writer, runtime, PUBLIC, anon and authenticated receive no EXECUTE. The wrapper uses the result only to accept or reject its own transition; it does not return the boolean to Admin or Teacher clients.

Both publication directions acquire transaction advisory locks keyed by `hashtext(fingerprint)` after shared actor → course → sorted blueprint → sorted assignment → sorted source/item locks. For multiple fingerprints, lock order is `(hashtext(fingerprint), fingerprint)` and duplicates are acquired once. Then the fixed existence check runs, and the lock remains through commit/rollback. Both paths use READ COMMITTED so the statement after a lock wait sees the committed winner; if a stricter isolation level is used, a serialization failure retries the entire publication transaction. A 32-bit hash collision only adds serialization because the query compares the complete fingerprint. Draft creation/edit needs no collision lock because it makes nothing learner-visible; publication is the checked visibility boundary.

Two-transaction trace across different assignments/courses:

1. Tx1 (Admin publishes assessment item A, fingerprint `K`) locks its course/blueprint/source, then the `hashtext(K)` advisory lock. The `PRACTICE` query finds no published practice membership or exposure and returns false. Tx1 publishes the approved assessment version and commits, retaining the lock through commit.
2. Tx2 (Admin publishes practice item B with a different item ID, assignment and course, but fingerprint `K`) locks its own target scope, then blocks on the same `hashtext(K)`. After Tx1 commits, Tx2 acquires the lock and runs the `ASSESSMENT` query in a fresh READ COMMITTED statement snapshot. It finds A's active published membership, returns true, and the practice transition aborts without exposing B.
3. Reverse the commit order and the `PRACTICE` query sees B's published practice membership or exposure; assessment publication aborts. If fingerprints differ, both queries return false and each operation may proceed. No existing row is needed for the lock to serialize competing first publications.

append_audit_event is executable only by the checked owners and verified denial wrapper. Only the assembly owner/service branch may emit SYSTEM assembly with no fabricated account, exact target/version/hash and sanitized correlation. Account invocation cannot choose SYSTEM. All source edits, assembly and publication share governance locks: actor when present → course → sorted blueprints → sorted assignments → sorted revisions/items → sorted assets. Teacher grading read follows the same relevant source locks; published/assembled consumer references never reopen original bytes. DB43-01–12 include both successful and denied principal paths; tests remain NOT EXECUTED.

For assembly and Admin approval/publication, source policies/checks include the effective greatest submitted revision per covered Lesson, then exact blueprint-generation item filtering (omitted scope/items never fall back) and retained REQUEST_CHANGES source-item exclusions. assembly_writer and its readiness/locker principals independently SELECT the exact relevant assessment review owner/action/feedback_item_ids plus source membership mapping needed to derive these exclusions; this grants no Teacher full-exam read. Empty feedback IDs expands to all members/source Lessons for exclusion and own-assignee worklist routing. New submitted successors supersede older source rows; invalid effective input cannot fall back. Request-changes shares the blueprint/source locks with assembly/publication. DB43-08 must prove an earlier-sorting rejected item cannot win or replay its returned version.
