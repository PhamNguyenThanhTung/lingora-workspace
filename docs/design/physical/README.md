## A. Physical architecture recommendation

Keep Supabase PostgreSQL, Supabase Auth and private Supabase Storage. Keep the two Next.js application boundaries with their in-process trusted backend. Keep Prisma 6 as the proposed ORM/migration owner in `lingora-admin`; the learner backend will consume the same generated mapping through a server-only data module under a later implementation plan. No technology migration or dependency upgrade is proposed. Actual inspected packages are Next.js 15.5.23, React 19.1.1, Prisma/client 6.19.3, `@supabase/ssr` 0.12.4 and supabase-js 2.112.3. PostgreSQL server version remains unverified; use features available in PostgreSQL 15 rather than claiming a live version.

Use unexposed `app` for domain tables and unexposed `app_private` for grading secrets, assessment responses, receipts, provisioning and audit. Neither schema is on the Supabase Data API exposed-schema list. Browsers use Next.js queries/commands; no direct application-table mutation and no browser DB credential. A dedicated non-owner, non-superuser, `NOBYPASSRLS` runtime login is used by Prisma. Migration owner is separate and unavailable to application processes. Supabase service-role key is confined to a small server adapter for staff provisioning/storage operations; it is not the normal domain-query connection. This is a proposed physical boundary, not evidence of existing deployment.

Every protected request verifies the Supabase subject, resolves the application account and rechecks current role/status. The server supplies only that verified UUID as transaction-local DB context. RLS resolves role/status from the protected account row. Authorization, RLS, secret separation and database immutability guards have distinct responsibilities; see the security matrix.

## B. Proposed table inventory and conventions

All 34 application tables below have a query/integrity purpose. They exclude provider-owned `auth.users`, `storage.buckets`, `storage.objects` and `_prisma_migrations`. Plural `snake_case`; link tables also use plural names. FKs use `<entity>_id`. Every table has a single UUID `id` PK, generated by database `gen_random_uuid()`, except `accounts.id` reuses `auth.users.id`. Version/revision/attempt/result/audit identities are independent UUIDs; user-provided UUID operation keys are deduplication identities, not authorization. Junctions use surrogate IDs plus natural unique constraints. Content logical identity survives all revisions.

Common columns: `created_at timestamptz NOT NULL DEFAULT now()` on every table. Mutable rows additionally have `updated_at timestamptz NOT NULL`, maintained by server/DB, and `row_version bigint NOT NULL DEFAULT 1 CHECK > 0` where specified. Immutable fact/link rows use their creation/domain timestamp and never fabricate an update timestamp. `?` means nullable; all other listed fields are NOT NULL. `FK` always means a real FK, not just a UUID-shaped string. Unqualified FK fields are UUID references to the named table id; locale-to-code is the explicit text exception. Lifecycle/status/source/action allowlists are text CHECKs; numbered ordinals are integers; is_* flags are booleans. Unless explicitly stated, FK action is `ON DELETE RESTRICT / ON UPDATE NO ACTION`; identities never change. Required strings reject blank values; ordered positions and revision numbers are positive integers. JSONB fields have an object/array CHECK as indicated plus versioned server validation; JSONB contains no relational ownership or authoritative IDs without validation.

## D. Auth / role / status model

`auth.users.id → app.accounts.id` is identity source; Supabase Auth owns credentials, verification and recovery. `accounts.role/status` are server-controlled trusted authorization fields. Exactly one role per account; no role array/conversion UI. Public signup creates only ACTIVE LEARNER, subject to provider email verification; client metadata may supply display name but never role/status. A restricted auth trigger creates the safe self-registration row in the same Auth transaction. Email remains Auth-owned.

For controlled staff creation, **skip-then-insert** is the selected proposal: an Admin-authorized private reservation of normalized email makes the auth trigger skip generic account creation for that address. Missing application account fails closed. The isolated Auth adapter creates a new provider identity carrying a server-written private operation-correlation marker, receives its UUID, verifies exact operation correspondence, then inserts fixed-role TEACHER/ADMIN with PENDING status. A public signup collision cannot satisfy that server-controlled marker and is never adopted/elevated or converted from LEARNER. The existing identity is reported for operator resolution. On lost provider response, reconciliation uses the private marker plus returned/provider-admin UUID; email equality alone is insufficient. Client-editable user metadata is never trusted. PENDING is supported by approved STA-01/UC-01; no further account lifecycle is introduced. The provider adapter must verify supported create/invitation correlation semantics in disposable integration tests before implementing this flow.

Teacher provisioning records the request, calls provider admin create/invite, binds exact Auth UUID, inserts PENDING account and success audit, then invitation activation transitions PENDING→ACTIVE after validated provider activation. The identity/DB/provider invite are not falsely described as one SQL transaction. Recovery looks up provider correlation/email in the controlled adapter; no blind retry create, no adoption of preexisting learner. Failure leaves missing/PENDING account denied and a retryable technical operation. Invite resend is distinct, bounded and may be at-least-once when provider gives no idempotent email delivery. Admin bootstrap uses a separately authorized operator and same fixed-role model. Admin never knows current password; recovery cannot enable a DISABLED account.

Protected request: validated Auth subject → account exists → ACTIVE and provider prerequisites → expected business role → ownership/current assignment and content/context curriculum scope → operation. Disable/enable increments row_version; next protected request rechecks DB without an authorization cache. Long-lived middleware session/JWT is not sufficient. An already running transaction may finish according to lock ordering; no instant token-revocation promise. Accounts missing during provision fail closed. Sensitive commands lock/recheck relevant account rows before committing.

## E. Curriculum/content/revision design

Admin manages hierarchy/order/requirement configuration; Teacher owns assigned lesson/item payload. Course/Unit visibility derives from available published lessons. A lesson is learner-available only when AVAILABLE and its active revision is PUBLISHED in active course. Published active required lessons remain in the denominator even when learner progression has not unlocked them. Unpublished, PLANNED, WITHDRAWN or inactive curriculum does not count as an unfinished requirement. Withdrawn completed history remains in history queries; current progress numerator only intersects the same current eligible set, preventing ratios above one. Zero eligible lessons returns unavailable/coming-soon, not fabricated completion percentage.

MVP sequential access uses configured unit/lesson order, prior core completion and working level; it does not equate availability with unlocking. Starting higher skips obligations for earlier levels without generating completions; earlier available lessons may be reviewed. Curriculum ownership fields (course language/framework, Unit course/level, Lesson Unit) freeze once an assignment, submitted/published work or learner evidence references them. Guards cover direct updates and ancestor changes that would alter effective scope. Position-only reorder inside the same scope remains allowed and increments course generation; it does not migrate historical evidence.

Teacher edits only unfrozen DRAFT/CHANGES_REQUESTED Lesson successors for the current assignment, using expected parent row_version. Add/update/remove lock the same assignment/parent and bump version. A narrow remove command deletes only unfrozen lesson exercise, vocabulary link or media binding associations. Submission permanently freezes payload, source items, keys and bindings. Request-changes records feedback; a successor revision carries editable corrections and prior_revision_id, never reopens source bytes. Assembled version membership has no Teacher edit/remove path.

Teacher submission has a concrete command path: `submit_assigned_work` checks verified ACTIVE Teacher, current Lesson assignment/episode, unfrozen editable state, readiness/media/tags, blueprint and assignment generations and expected parent row_version. It locks actor → course → sorted blueprints → assignment → source/items/assets, then atomically sets submission metadata, freezes source bytes/children/keys, stores episode/scope, appends SUBMIT/audit and records a receipt. Teacher cannot approve/publish or submit an assembled version; Admin transitions are separate.

Exact practice-item reuse is blocked conservatively at assessment submit/publish: reject PRACTICE origin, any practice-exposed item revision and any equal canonical content/key fingerprint appearing in a practice membership or exposure registry. No extra QuestionBank: registry is item identity/revision plus membership query. Every draft fingerprint creation/change, membership attachment, submit, publish and practice exposure path acquires a PostgreSQL transaction advisory lock keyed by a stable 64-bit hash of the canonical fingerprint, sorted when multiple fingerprints are involved, then rechecks collision/membership eligibility. Hash collisions merely serialize extra work. This protects even an absent collision row and is a local PostgreSQL lock, not distributed infrastructure. Old and new fingerprint keys are both locked when an editable item changes. Assessment publication and practice publication/exposure use the identical key convention. A practice candidate matching an already-published assessment fingerprint cannot become answer-exposed; create a different variant. Reserve all published PRACTICE fingerprints as exposed candidates so later assessment publication cannot race first feedback. Service/functions/triggers mandate this lock convention on all writes; raw bypass writes are denied. Concurrent absent-item creation/publication is an acceptance test. An ASSESSMENT item can never join practice. New variants must differ in prompt/key/media semantic fingerprint; testing the same vocabulary/skill is permitted. Media includes transcript/key content in secret storage, not learner asset metadata. Human review catches semantic copying not detectable by the deterministic normalization.

## F. Lesson attempt / completion / performance design

Server creates attempt pinned to active lesson revision and actual N core membership. The queue is all first answers in order, followed by the first-wrong items in original response order; retry once regardless of retry correctness. Each command locks attempt, validates next queue member, authorizes own ACTIVE context, grades from secret data, appends one response and returns formative practice feedback. Invalid/duplicate payload does not add a response. Same operation retry returns recorded safe feedback, reconstructed from immutable grade/data, without advancing queue.

Complete command validates all N first responses and exactly K retries, recomputes units/N/K/count, finalizes performance, inserts first completion ON CONFLICT without changing provenance, enrolls core vocabulary with no-reset upsert, stores qualifying local day/timezone and receipt, all in one DB transaction. No score gate. Latest completed score is ratio from latest attempt, not the first completion row. An open attempt is not completed performance. For a new first completion, the finalizer locks the same course row used by replacement and requires the pinned revision still be the active AVAILABLE revision before any performance/completion/SRS/day/receipt write. If replacement wins, the old attempt and responses remain open with no partial side effects; a fresh attempt uses the active revision. If finalization wins, its valid completion commits before replacement. After identity/ownership/status checks, **dedupe before** the now-stale active-pointer check: an identical retry of a committed finalization returns its receipt. Existing completion facts are never overwritten. Completion failure rolls all linked writes back; redo gets a new attempt while the unique first completion remains unchanged.

## G. SRS design

Learner+Vocabulary unique account-wide. Enrollment from completed core vocabulary or explicit optional selection uses ON CONFLICT DO NOTHING, preserving existing schedule. Five stage indexes encode approved Policy B; server time controls due_at. A SCHEDULE operation locks the card, checks operation key/hash and the unique card/session identity, stores before/after and updates the card once atomically. A REINFORCEMENT has its own idempotency key and must reference the forgotten SCHEDULE in the same signed session. Partial uniques allow at most one schedule and one reinforcement per card/session; parent uniqueness remains a second guard. Reinforcement records UI/evidence without updating the card or qualifying day. An intentional later review uses a new session. Stage5 remains recurring +30; FORGOTTEN stage1/+1. No SM-2 parameters, probability authority, client timestamps or client schedule.

Streak is distinct local dates UNION of completed lesson attempts (including valid redo) and SRS SCHEDULE operations across all languages; assessments, incomplete lessons and optional mere enrollment are excluded by ADR-033. Timezone is account-global validated IANA preference. Store the date/timezone observed at successful activity, so later preference change cannot silently reassign historical activity dates. Count consecutive qualifying dates ending today, or yesterday if today has no qualifying fact; missing a day breaks the sequence. No summary persistence, freeze feature or hard-coded timezone. Review must confirm this technical historical-date choice without adding assessment qualification.

## H. Assessment design

Admin configures blueprint scope/coverage/config. Teacher submits Lesson-bound contributions; the system assembles complete eligible submitted inputs, then Admin reviews/approves/publishes (ADR-043). Blueprint scope freezes once assembly uses it; different scope requires a new blueprint, with contributions submitted under the existing relevant Lesson assignments. Non-scope config increments generation. The immutable version snapshots all purpose/scope/coverage/catalog/distribution/grading policy and exact source submissions; attempts pin it before grading. No lead Teacher or separate blueprint assignment. See [assembly/correction/security rules and DB43 acceptance](database-reconciliation-2026-10-20.md). Only PLACEMENT/LEVEL_UP active; current curriculum gate remains separate from pinned pass policy.

Start validates available version, own ACTIVE context and the version's immutable scope. Finalize validates item set/timing/input and topic/skill coverage, grades privately from pinned version data, writes private responses/result and marks attempt complete in one transaction. Any current curriculum gate remains a separate check. Retry with the same submission key/hash returns the same aggregate result; changed payload/key reuse is rejected. New intentional attempt produces new immutable result. Missing/invalid submission leaves no result. Queries allow aggregate own result only; no per-item correctness, keys or answer-revealing explanation during or after assessments. Version coverage/purpose stays reproducible after later blueprint configuration changes.

Completed Placement provides a recommendation. Selecting it is an explicit learner action or the same confirmed selection command: lock context, require expected context row_version and own result, update selected starting level/source/result atomically with receipt. Incomplete Placement never modifies a valid starting point. Concurrent self-report/another selection wins only by optimistic version; stale request gets conflict and keeps evidence, not silent overwrite. Completed recommendation alone is not a verified proficiency or level-up.

Level-up finalization locks course/context/attempt, rechecks the currently configured curriculum gate under course generation serialization, evaluates assessment against pinned version pass config, creates result and advances working level only if both gates hold and transition still matches. Already advanced/stale working context retains result with no repeated progression; no downgrade or starting-history rewrite. If readiness/config scope changed and gate no longer holds, return conflict before creating completed result so learner can retry the valid operation after resolving it; do not invent a partially applied pass result. New unavailable next-level content still renders coming-soon rather than granting nonexistent lessons.

Assembly first resolves the greatest submitted revision_no per covered Lesson, then filters its items by blueprint identity/generation; the complete submitted Lesson snapshot supersedes every older contribution (omissions mean no contribution), while an unsubmitted draft does not. Rejected/withdrawn/stale effective sources cause unmet requirements, never fallback. REQUEST_CHANGES version feedback excludes its affected source item revisions; empty feedback IDs expands to every member for exclusion and routing to all source Lessons. Corrections submit successor sources/new item revisions. Stable-ID selection happens only after these filters. Approval/publication rechecks source precedence/exclusions under the same locks; input-hash retry cannot resurrect a returned version. See DB43-08.

## I–K. Assignment, media and audit

Assignment has one stable Lesson target and ordered immutable history episodes. Creation pins its episode/author; submission/review pins applicable episode and current requirement/scope generation. Reassignment preserves provenance while transferring access. Scope changes make stale approvals unpublishable. Assembly consumes submitted frozen Lesson contributions; publication checks each source generation and the blueprint generation under shared locks. Feedback follows source Lesson to its current Teacher; corrected sources yield a successor assembled version.

Use existing private `lingora-media` and `lingora-avatars` buckets. No overwrite/upsert of bytes; replacements have new asset IDs/keys. Upload authorization is scoped to current assigned Teacher. Publication requires ready, hash-verified and unretired assets. Every binding/avatar-reference acquisition locks its asset and rejects non-null `retired_at`; publish locks its bound assets in sorted ID order and rechecks. Cleanup reserves retirement in a transaction by locking the asset, checking no media binding/avatar reference exists, then setting `retired_at`. The retirement reservation blocks future references. The worker rechecks reservation/no references, commits, performs a **final reference check**, then calls Storage delete **outside the database transaction**. A timeout preserves the tombstone and retries idempotently against the immutable key; missing object is success. This uses one bounded cleanup command/process and no queue/table subsystem. Published content uses private authorized streaming; no public draft URL or learner access to grading/transcript objects.

Audit actor/action/target/version/outcome/reason/time plus safe correlation is append-only; Admin reads a bounded query ordered by `occurred_at,id`. Success audit commits with the domain transition. A verified Auth subject with no application account is denied protected access but can be recorded using `verified_auth_subject_id` and null `actor_id`; the narrow audit writer appends that denial after rollback. No phantom account is created. Exclude passwords, tokens, keys, raw learner answers and assessment feedback. Retention duration is deferred. Assignment/review provenance stays in domain history.

## L–M. Critical constraints and enforcement

See the full [resource/RLS matrix](security-and-rls.md). Direct browser DELETE and generic runtime delete are denied. One narrow Teacher command may delete only a unfrozen draft association row from an assigned DRAFT/CHANGES_REQUESTED Lesson package; the entity, item, asset bytes and all published/evidence/history rows remain. No cascade from account, lesson, context, revision/version or vocabulary into history; retained domain FKs are RESTRICT/NO ACTION. Provider object deletion is separate and allowed only after atomic retirement reservation proves no references and blocks new ones. An eventual learner-data purge/anonymization policy requires separate approval.

PostgreSQL CHECKs cannot reliably enforce facts in other rows; [PostgreSQL 15 constraints](https://www.postgresql.org/docs/15/ddl-constraints.html) distinguishes FK/unique/check responsibilities.

## O. Transactions, concurrency and idempotency

Fixed learner lock order remains actor → course (when sensitive) → context → attempt → sorted cards. Governance order is actor when present → course → sorted blueprints when needed → sorted assignments → sorted source revisions/items → sorted assets. Assembly has no business actor. Source operations without blueprint access never acquire blueprint locks afterwards. Publish/assembly lock all required sources in the same order and recheck generations/readiness/row versions. Cleanup locks only its asset and never locks parent rows. Existing scoped-locker/learner-writer lock privileges and FORCE RLS context lookup remain required; no generic curriculum mutation is granted. Provider calls occur after commit.

| Operation | Retry safe? | Strategy and transaction boundary |
|---|---|---|
| Lesson answer | Yes, identical operation | attempt row lock; UNIQUE attempt/key and exercise/ordinal; input hash; append once, return same feedback |
| Lesson completion | Yes | receipt + attempt state; finalize/first completion/core SRS enrollment/day/audit if required atomic |
| First context create/resume | Yes | actor lock then course lock; own-context lookup; UNIQUE learner/language; count ACTIVE contexts and insert/update in same transaction |
| System assembly | Yes | blueprint-serialized complete input validation; source submit/episode pins, immutable members, input-hash uniqueness and SYSTEM audit atomically |
| Teacher edit/remove/submit | Yes | current Lesson assignment + unfrozen editable successor + row_version; submit pins episode/scope and freezes all source bytes |
| Assessment submission | Yes | own submission key/hash; lock context/course/attempt; private responses/result/progression/finalized atomic |
| SRS scheduling/reinforcement | Yes | learner/key hash; lock card; history and schedule atomic; reinforcement parent unique and no schedule write |
| Publish lesson | Yes | actor/key receipt; lock course/assignment/lesson/revisions/assets; validate approved assignment generation/snapshot and media reservation; switch active revision atomically |
| Publish assessment | Yes | actor/key receipt; lock course/blueprint, sorted source assignments/revisions/assets; compare every source scope pin + blueprint generation; atomic active-version switch |
| Retire media | Yes | lock asset, verify no bindings/avatar reference, set retired_at reservation; commit; final DB check; provider delete outside transaction; retry tombstone safely |
| Disable/re-enable | Yes | fixed desired state and receipt; target account lock/status/audit atomic; wrong payload with same key rejected |
| Staff provision/invite | Identity retry safe; email not exactly-once | private operation/email reservation + provider correlation + reconciled auth UUID; PENDING until activation; no SQL/provider atomicity claim |
| Start selection | Yes | receipt + expected context version + own complete Placement or self/default config; context update atomic |
| Teacher assignment/reassignment | Yes | receipt + assignment version lock; current assignee/history/audit atomic |

Replacement validation happens before clearing old pointer/active flag; all updates share one transaction. Crash/constraint failure rolls back old active state. No intermediate committed zero/two active versions. Explicit withdrawal is distinct: allowed to remove availability/pointer atomically while preserving old history. Teacher concurrent editing uses row_version predicate; every child edit locks/version-checks parent and increments parent version. Submit/review also compare parent version, not just child's updated_at.

Course-generation changes (ordering, eligibility, gates, withdrawal/publication, default-resolution inputs) use the same course lock as learner access/finalization and first-context initialization. Curriculum ownership FKs are immutable once referenced; ordering changes retain scope. Assessment payload/scope remains pinned; current readiness is separately rechecked at Level-up commit. An old lesson attempt may create the first completion only if its revision remains the active AVAILABLE revision at the shared course lock; already committed completion retries replay their receipt after authorization. SRS card/session uniqueness covers concurrent distinct parents as well as identical retries.

## P. Prisma / Supabase runtime mapping

Each inventory row maps to one Prisma model with `@@map` plural table name and schema annotation for `app` or `app_private`; model fields may be camelCase only in TypeScript while DB identifiers remain snake_case. `accounts` combines User/Profile; provider Auth/Storage are not managed as Prisma-created tables. SQL-only FK `accounts→auth.users`, trigger/helper/grant/RLS/partial unique/CHECK/immutable guards belong to future hand-authored migration SQL; ORM schema alone cannot represent deployment security. FKs to provider tables are recorded in migrations even when not exposed as managed Prisma models. No production Prisma edit here.

Enum candidates: BusinessRole (three values), AccountStatus (three including authorized PENDING), ContextStatus, StudyFocus (five controlled values), ContentStatus, ExerciseType (five), AssessmentPurpose (two), SrsRating (two), SrsOperationKind, Availability. Finite operation enums do not add product states. Proposed CHECK-based text representation makes SQL baseline readable; final review may choose native enums without changing values. Numeric assessment points map Decimal; timestamptz and UUID use native types; JSON blocks validated before persistence. No middleware auto-injecting userId as a substitute for authorization.

Prisma transaction wrapper is proposed to use one interactive transaction/connection; it sets a transaction-local verified subject and performs a fresh account check. No session-global state or client-selected subject/role. The proposed domain login is non-owner/NOBYPASSRLS, with ENABLE/FORCE RLS on tables; this is design intent, not verified runtime behavior. A service-role connection bypasses RLS and is confined to provider tasks; server authorization remains mandatory on every path. Narrow function principals have explicit checks and grants; actual role flags, policies, grants and session behavior require future catalog/integration verification.

Existing `DATABASE_URL` historically points at an owner-like `postgres` shared session pooler user; replace its runtime use later with least-privileged dedicated connection. Keep a separate migration credential/config; no runtime migration permission. Session-mode pooler is the existing declared connection baseline; do not assume transaction-pooler compatibility or deployed grants. Public Auth key used for validated sessions, service key only controlled server adapter; browsers never receive Prisma credentials. Supabase service-role credentials bypass RLS, so the adapter must authorize before provider calls ([Supabase RLS documentation](https://supabase.com/docs/guides/database/postgres/row-level-security)).
