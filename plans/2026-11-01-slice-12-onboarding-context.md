## Contracts

### A: Registration, confirmation and safe first login

- `/register` public UI and `POST /api/auth/register`: strict `{email,password}` (optional bounded displayName only if useful), email/password provider-appropriate validation; same-origin JSON mutation, generic safe errors and no credential/session values in response/logs. Call the existing request-scoped Supabase SSR client's `signUp`; provider owns unique email, confirmation and credential persistence. Duplicate/unconfirmed retries must not create multiple app Accounts or leak identity. Render confirmation instruction and login link; never promise logged-in success on unconfirmed signup.
- Narrow `/auth/confirm` GET handles existing SSR PKCE `code` exchange; if token_hash route is supported allow only fixed signup/email confirmation type (never invite/recovery). Do not accept next/open redirects; destinations fixed `/login` success/error message. Preserve HttpOnly/cookie/header namespace. Confirmation does not create/activate an app Account and does not weaken verified-email checks. Missing/expired/replayed/provider-failure states are safe, retryable where meaningful. Do not alter provider templates/allowlists; document required callback configuration and distinguish local protocol tests from real inbox proof.
- Existing password login: after provider success, invoke a narrow bootstrap that independently obtains a fresh `getUser()` and requires email + email_confirmed_at. If Account already exists, do not alter any field; existing verifier remains authoritative for role/status. For missing UUID, transactionally reject trusted private app_metadata staff marker and any private ProvisioningRequest matched by normalized verified email, authUserId or planned providerCorrelationId. Insert fixed LEARNER/ACTIVE with schema defaults and activation time; ON CONFLICT DO NOTHING then re-read. Never adopt a client UUID/email/role/status/user_metadata role, convert staff or reactivate DISABLED/PENDING. Existing Teacher/Admin provisioning/activation source unchanged. Existing missing-account verification outside the login bootstrap remains fail-closed.
- Auth service exposes a testable small helper; no general auth redesign. Safe 503 on database/provider failure; failed login must keep existing local-session signout/namespace cleanup.

### B: Context options, create and desired-state lifecycle

- Existing `GET /api/learner/context` keeps behavior. Extend summary DTO additively with `rowVersion: string` and `startSource: string|null` (update fixtures/consumers truthfully).
- `GET /api/learner/context/options`: verified ACTIVE Learner only; safe projection of learnable Languages, active Courses and eligible published-content Levels, sorted deterministically; defaultLevelId|null and honest empty/coming-soon. No grading keys or draft payload. Existing context ownership/role/status guards apply.
- `POST /api/learner/context`: strict union `{contextId:UUID,languageId:UUID,courseId:UUID,startSource:'DEFAULT'}` or same with `startSource:'SELF_REPORT',levelId:UUID`. Reject extra keys. Client generates contextId ONCE per create operation, retaining it across transport failure/retry. It is dedup identity, never authority. Store existing fields only. No receipt framework/table or immutable history required for this command.
- Same id/same owned initial selection replays persisted row; conflicting reuse or existing other id for same learner/language returns409, never duplicates, resets or implicitly resumes. Replaying DEFAULT does not re-resolve/overwrite persisted start after catalogue changes; still recheck current actor/security. Foreign id gives opaque conflict/notfound without leaking owner. Explicit SELF_REPORT compare selected level to request. Serialized create writes at most one context and zero consumption/attempt/completion/SRS/result rows.
- Transaction: lock/recheck Account (`FOR NO KEY UPDATE`) -> Course -> relevant Language/Level/publication parent locks with consistent ordering -> context lookup/count/insert. Revalidate candidate exact active published Lesson after its shared lock before deriving selected level; protect course/language/level scope against concurrent invalidation. Reuse actual existing lesson publication predicate. No stale option trust. Two-ACTIVE enforced under actor lock for create/resume, including simultaneous different-language create/resume. Raw SQL parameterized; existing FK/unique/checks retained.
- `PATCH /api/learner/contexts/[contextId]`: strict `{status:'ACTIVE'|'PAUSED',expectedRowVersion:positive bigint decimal string}`; actor→Course→owned context lock order, fresh ACTIVE LEARNER check. Foreign404. Desired-state/CAS: expected version succeeds (no-op if already desired; otherwise version+1). Same desired status with exactly expected+1 can replay the already applied transition; any other stale version409. Never replay an older pause across a later resume. Resume obeys two-ACTIVE and course/language scope; pause remains possible when course becomes inactive. Update status/rowVersion/updatedAt ONLY.
- PAUSED denies reading start/complete and Practice start/respond/finalize, including committed replay where existing policy requires current access. Existing parent/account locks must serialize pause versus in-flight learning: first lock winner may finish, next request sees paused. Read/list owner context stays available to resume. No learned-history delete/rewrite/reset.
- Product UI: integrate small create form into HomeView (also empty state), Language→Course→DEFAULT/SELF_REPORT Level controls with clear provisional label, no Placement placeholder. Preserve operation identity/input on failure, disable duplicate pending actions, handle401/403/409/503 and retry/reload. Cards show pause/resume with rowVersion and authoritative response reconciliation; ACTIVE+course available links into existing `/learn/[contextId]`. Home existing no-data/denial/logout behavior preserved. Do not redesign other accepted pages.
