## Context

M1.6W Web learner foundation has completed implementation and is in TESTING.

Two protected-hop tests:
- `M1.6W-T-006` — SRS
- `M1.6W-T-007` — Roleplay

failed with HTTP `401 Unauthorized`.

Live evidence confirmed the root cause:
- Supabase currently issues `ES256` JWTs containing a key ID (`kid`).
- M1.5 currently only verifies JWTs via `HS256` with `SUPABASE_JWT_SECRET`.
- An HMAC secret cannot cryptographically verify an ES256 elliptic-curve signature.
- Requests from Web successfully reach FastAPI.
- M1.5 starts successfully with `MOCK_MODE=true`.
- SRS/NLP mock services are ready.
- There are no Web errors; Web implementation does not need modification.

The objective of this amendment is to update M1.5 authentication verifier to validate JWTs issued by the live Supabase project.

## Objective

Update the JWT verification logic in `lingora-ai/api` to support:

`Supabase ES256 JWT -> kid -> Supabase JWKS -> public key -> signature verification`

After amendment:

`M1.6W Route Handler -> FastAPI M1.5 -> JWT ES256 verification -> SRS/Roleplay`

must function cleanly without changing any Web implementation.

## Required Design

The updated verifier in `lingora-ai/api/app/auth.py` will:
1. Extract Bearer token from the `Authorization` header.
2. Read the unverified JWT header to obtain `alg` and `kid`.
3. Support `ES256` via Supabase JWKS public key resolution (using `jwt.PyJWKClient` / `PyJWT[crypto]`, which is already available in the runtime).
4. For backward compatibility with existing unit test suites and offline scenarios, permit `HS256` verification against `SUPABASE_JWT_SECRET` when `alg == "HS256"`.
5. For `ES256`:
   - Resolve the public key from the trusted Supabase JWKS endpoint (`SUPABASE_JWKS_URL` or derived `{SUPABASE_URL}/auth/v1/.well-known/jwks.json`).
   - Cryptographically verify the signature, expiration (`exp`), subject (`sub`), and role (`role == "authenticated"`).
6. Reject with HTTP 401:
   - Missing or malformed Authorization header
   - Invalid signature
   - Expired token
   - Unknown `kid`
   - Unsupported algorithm (e.g. `none`, `RS256` if not in JWKS)
   - Malformed JWT string
   - Missing `sub` or invalid `role`
   - JWKS unavailable / fetch failure (fail closed)
