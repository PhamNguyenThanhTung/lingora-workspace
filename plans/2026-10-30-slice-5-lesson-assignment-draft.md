## Verified data contract

- `Lesson`: UUID PK, required `unitId`; Course and Level derive through Unit. `position` positive int32, unique `(unitId,position)`; `isRequired=true`; `availability=PLANNED` (other actual values AVAILABLE/WITHDRAWN). `rowVersion` BigInt defaults 1. No Lesson title/code/slug/body/objective/duration or translation table. Admin creates skeleton with position/isRequired only; availability and activeRevisionId remain server-owned. `activeRevisionId` identifies published content, never the current draft.
- `ContentAssignment`: one per Lesson (`lessonId` unique), UUID PK, `createdBy` Admin, `currentTeacherId`, JSON requirement/scope default `{}`, `scopeGeneration`, `rowVersion`, timestamps. Reassignment updates this row, retaining creator/requirement/scope.
- `AssignmentHistory`: immutable episodes, unique `(assignmentId,sequenceNo)`, eventType ASSIGNED/REASSIGNED/SCOPE_CHANGED, previousTeacherId nullable, nextTeacherId, scopeGeneration, changedBy, scopeSnapshot and timestamps. First assignment creates sequence/generation 1, ASSIGNED and previous null; reassignment increments both generation and sequence, REASSIGNED with old/new teachers. Set changedBy to verified Admin; snapshot `{schema_version:1,requirement:<server JSON>,scope:<server JSON>}`. Same-teacher request is an authoritative no-op after concurrency/auth checks, without fake history. No SCOPE_CHANGED feature.
- `LessonRevision`: UUID, `(lessonId,revisionNo)` unique; required assignmentId and creationAssignmentEpisodeId composite FKs, optional priorRevisionId same Lesson and earlier number. `createdBy` MUST equal creating episode.nextTeacherId (corrected migration); `lastEditedBy` is saving Teacher. Title is JSON object, contentBlocks JSON array. Status actual values DRAFT/IN_REVIEW/CHANGES_REQUESTED/APPROVED/PUBLISHED/ARCHIVED/WITHDRAWN. Only new DRAFT records are created here.
- Revision content includes topicIds/skillIds/purposeTags and optional coverageCatalogGeneration/coverageSnapshot. Submission/approval/publication/generation/scope snapshot fields are server-controlled. Ever-submitted source payload is frozen by closure migration. Do not edit or delete existing saved revisions, including old DRAFTs.

## Authoring contract: minimal and loss-safe

The schema checks JSON container types but has no concrete paragraph format. Adopt an application-level subset for this slice, not a claimed DB-wide format:

- Title editor exposes `vi` and `en` string fields, trimmed; at least one nonempty, max 300 chars each. Preserve all other existing string locale keys unchanged, server-side. A pre-existing title with nonstring values is unsupported/read-only, never coerce it to strings.
- Content editor supports zero or more ordered plain paragraphs (add/remove paragraph textareas), persisted exactly as `[{type:"paragraph",text:"..."}]`; each object strict, text max 20,000 chars, at most 50 paragraphs, aggregate request max 1 MiB. Render as React text, never HTML. Empty array permits an initial draft with title only. Do not join/split existing blocks or discard unknown keys.
- Change summary is optional, trimmed, max 500 chars. No arbitrary JSON editor.
- On successor saves preserve server-read topicIds/skillIds/purposeTags/coverageCatalogGeneration/coverageSnapshot without exposing them for editing. Never copy client versions of these fields.
- Reject save with recoverable 409 `UNSUPPORTED_DRAFT_CONTENT` and show an explicit read-only reason when highest revision has unsupported title/block structure or revision-attached associations (exercises, vocabularyLinks, mediaBindings, authoredItemRevisions, attempts, assessmentVersionItems). Check actual relation counts. Do not create a successor that silently drops associations. Existing history remains readable with safe labels; do not crash list rendering on unsupported JSON.

## Concurrency, ownership and transaction contract

Use `Lesson.rowVersion` as one aggregate CAS token for all metadata edits, assignment writes and draft saves; serialize to positive decimal string `rowVersion` in DTOs, accept strict `expectedRowVersion` string. Do not cast BigInt to Number. Initial create has no expected token. Missing/invalid token400; mismatch409 `STALE_LESSON`. All successful changed writes increment once and return authoritative aggregate DTO. Independent tabs, metadata edits, reassignment and saves must conflict rather than overwrite silently.

Each mutation uses one DB transaction: lock actor/target Account rows in stable UUID order (parameterized SQL, `FOR NO KEY UPDATE`), recheck actor exact role and ACTIVE; assignment target exact TEACHER/ACTIVE; then lock Lesson (`FOR UPDATE`), verify current Unit/Course context and expected version, then assignment/history/revisions. For create lock/recheck Admin and validate Unit/Course inside transaction. Account locks coordinate with accepted disable/enable row locking: a disable that wins first denies assignment/save; a save that wins first completes before disable. NO KEY UPDATE still serializes status changes but permits FK key-share checks when another assignment/audit references a locked Account, avoiding an Account→Lesson / Lesson→FK-Account cycle. This follows the [PostgreSQL row-lock compatibility contract](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-ROWS). Recheck runtime role/status, do not rely only on an earlier helper result. Use stable order across new operations and rollback on any later failure. Do not alter accepted lifecycle globally.

- Admin routes/pages require accepted ACTIVE ADMIN helper. Teacher routes/pages call accepted helper plus a local exact `role === TEACHER` check: `verifyStaffIdentity(requiredRole:'TEACHER')` also allows ADMIN today. Preserve global auth behavior.
- Teacher detail/save query by Lesson AND `assignment.currentTeacherId=actor.id`; unrelated ID returns404, never disclose its title/context/history. List only assigned Lessons. Disabled access fails accepted403 ACCOUNT_INACTIVE; Admin is forbidden on Teacher endpoints.
- All nested Admin requests require Unit.courseId matches URL and Lesson.unitId matches URL (404 on missing/mismatch). Immutable parent IDs never accepted in body.
- Assignment first-create and history insert are atomic; reassignment/history/generation/version increment are atomic. Existing assigned disabled Teacher remains displayed with status; options contain only active Teachers. Disabled assignment persists and re-enable restores access. Target tampering rejected even if UI filters correctly.
- Current revision always means highest revisionNo across ALL statuses, not highest editable/fallback old DRAFT. Save only if no revision or highest is DRAFT and has never been submitted (`submittedAt`, `submittedBy`, submittedAssignmentGeneration, assignmentScopeSnapshot absent; reject inconsistent workflow provenance too). Highest non-DRAFT is read-only409 `DRAFT_NOT_EDITABLE`, even if older DRAFT exists. Never transition CHANGES_REQUESTED here.
- Each save inserts next revision `max+1` (first1), priorRevisionId=current highest (first null), current assignment and latest current episode. Verify episode matches assignment/current Teacher/current scopeGeneration; inconsistent/missing history fails409, do not invent a repair episode. Set createdBy/lastEditedBy to saving Teacher; status DRAFT; old revision bytes unchanged. After reassignment successor may point at prior Teacher's DRAFT, but new provenance belongs to new episode/Teacher. Leave activeRevisionId unchanged.
- SQL locking/CAS and transaction rollback are real behavior, not only mocked success paths. Map unique position conflicts to409 `DUPLICATE_LESSON_POSITION`; revision/assignment races to recoverable409; unexpected provider details stay server-side.

## Routes, DTOs and UI

Follow existing same-origin, content-type/JSON, UUID (all canonical UUID variants), no-store/private, auth-refresh cookie/header and `{error:{code,message,fields?}}` conventions. Strict Zod bodies reject unknown/server-owned keys.

- `GET .../lessons/teacher-options` — authenticated, parent-scoped ACTIVE TEACHER account IDs/displayNames only; do not expose email/provider secrets or broaden existing management API. Current assigned disabled Teacher remains represented in Lesson DTO.

- `PATCH /api/teacher/lessons/[lessonId]/draft` — `{title:{vi?,en?},contentBlocks,changeSummary?,expectedRowVersion}` only. At least one supported title is required; merge other locales from highest server revision. No assignmentId/status/parent/provenance fields in input.

Shared serializable Lesson summary contains id/unitId/position/isRequired/availability/rowVersion, Course+Unit labels/context, assignment (id/currentTeacher id/displayName/status/generation), highest revision summary (or null) and editability reason. Detail adds supported current title/content and minimal descending revision history (number, author, timestamp, summary, status); null current revision is “Chưa có bản nháp”, not an invented persisted status. Dates ISO, versions decimal strings. Mutation response uses same detail/summary contract, catalogue/editor reconcile from returned DTO, no optimistic fabricated success.

Forms use explicit Save, duplicate-submit/dismissal locks while pending, retain input on validation/network/409/503 failure, visible retry and conflict explanation. A stale editor must reload/reconcile current token before retry; do not silently resubmit stale content with a new token. Existing401 session-lost and403 forbidden flows must release modal/inert state so Logout remains usable. Dependency option failures are recoverable and preserve values. Reuse accepted components/utilities where suitable; no giant harness or generic multi-role endpoint.
