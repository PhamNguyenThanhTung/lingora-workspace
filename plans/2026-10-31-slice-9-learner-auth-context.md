## Learner auth and session contract

Routes: `/login`, protected `/home`, root `/` redirecting to `/home`, `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/learner/context`, all on the learner origin. Login uses actual Supabase `signInWithPassword`, then fresh `getUser()` and fresh Account lookup by verified user UUID. Dedicated `verifyLearnerIdentity` requires exactly `LEARNER`, exactly `ACTIVE`, and confirmed email. Caller data/metadata never controls role/status/subject. Do not call `verifyStaffIdentity` as a learner guard.

Implement request-scoped SSR client and proxy refresh with the accepted transport semantics: cookie `getAll/setAll`, refreshed cookies forwarded to downstream render, SDK Cache-Control/Expires/Pragma preserved on success/alternate responses, and private/no-store on protected HTML/API. Own cookie namespace (including chunk suffix handling), `httpOnly: true`, `sameSite: lax`, `secure` on HTTPS, host-only, path `/`; no cross-app Domain cookie. No browser Supabase client is needed. Use separate browser contexts for role tests; localhost ports alone do not isolate cookies. Logout clears only learner auth cookies even during provider failure and redirects to learner `/login`. Protected requests always recheck identity/Account; middleware refresh alone grants no access.

- Missing/expired/invalid provider session or wrong password: 401 (`UNAUTHENTICATED` / `INVALID_CREDENTIALS`). Refreshable expired access tokens follow normal Supabase refresh, not unconditional rejection.
- Authenticated but Account missing or wrong role: 403 `FORBIDDEN`; PENDING/DISABLED: 403 `ACCOUNT_INACTIVE`; unconfirmed identity: 403 with safe confirmation message. Do not auto-create/repair accounts. Failed role/status login signs out the learner-origin session.
- Provider/database outage: 503 `SERVICE_UNAVAILABLE`, retryable, no false success. No raw provider/SQL details.
- Home redirects only 401 to learner `/login`; 403 renders accessible denial/logout, 503 renders retry. Login with a valid learner redirects `/home`; authenticated forbidden identity does not create a redirect loop. Every protected context request repeats guard checks, so disabling a logged-in Account blocks its next request without requiring provider revocation.
- Both auth mutations validate same Origin and JSON input (login), use fixed local redirect destinations, preserve pending/error/focus/keyboard behavior. No open `next` redirect, OAuth callback, email link callback, activation, or provider redirect is introduced: password sign-in establishes the SSR cookie in its response, then the actual login component navigates to `/home`. Therefore Supabase learner Redirect URL additions are unnecessary for this slice's flow; record this applicability and inspect existing allowlist without removing staff `/activate-teacher` or local entries. Public navigation/logout must remain on the learner origin, never localhost/staff.

## Actual learner context model and DTO

`LearningContext` is the existing learner-to-course association; there is no separate Enrollment model or current/default context pointer. `learnerId`, `languageId`, and `courseId` are required; UNIQUE(learnerId, languageId) permits multiple languages/courses per learner. Status is ACTIVE/PAUSED. Course.languageId must equal context.languageId; selectedStartLevel/workingLevel, when present, belong to Course.frameworkId. Nullable starting-point shape is enforced by existing checks: no startSource means selectedStartLevel, startResult, selfReport, workingLevel all null. Existing scope trigger verifies PLACEMENT result ownership/finalization/level when that branch exists. Read-only scope here does not add creation/resume, ACTIVE capacity, preference or placement behavior.

`GET /api/learner/context` has no selector parameters or body; reject unsupported selectors with 400. Always query contexts by verified Account UUID, with explicit selected fields and defensive ownership/scope checks. Same guarded loader feeds production home and API; do not use a client-supplied learner/account ID or generic Prisma serialization.

Response envelope:

```text
{ data: {
  learner: { id, displayName, role: "LEARNER", status: "ACTIVE", uiLocale },
  contexts: [{ id, status,
    targetLanguage: { id, code, names },
    course: { id, names, isActive },
    framework: { id, code, version, names },
    selectedStartLevel: { id, code, label, position } | null,
    workingLevel: { id, code, label, position } | null
  }]
} }
```

Stable order: createdAt then id, without asserting a business current/default choice. Required now: guarded identity and owned contexts with language/course/framework, safe level summaries if present. Optional: displayName and both levels. Deferred: preferences, purpose, start/placement result payload, enrollment edits, attempt/progress/SRS, locale editing and context selection. Never infer current level from Course.defaultStartLevelId or fabricate placement data. No email/Auth metadata, native-language/avatar internals, timestamps/row versions, practice/gate config, grading/content secrets, or another learner's fields in this DTO.

Zero rows is successful 200 `contexts: []`; home says “Bạn chưa có lộ trình học.” and keeps Logout usable. Present contexts with null levels, PAUSED contexts, or inactive courses remain authentic owned context summaries with clear labels; they do not become auth failure or imply lesson eligibility. Home shows own name/identity plus each real course/target language and existing level labels, with no learner lesson catalogue or analytics. A malformed owner/course-language/framework/level join must fail closed as 409 `CONTEXT_INCONSISTENT` with safe support/retry UI, not empty success/auth redirect/500. Check relations required for this summary; do not join deferred assessment history merely to add validation scope. SQL constraints make genuine wrong-parent live inserts inappropriate; use isolated query doubles for corruption tests, never disable constraints/triggers.
