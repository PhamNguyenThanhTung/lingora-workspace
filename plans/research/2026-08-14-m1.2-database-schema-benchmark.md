# M1.2 Database Schema Benchmark for Lingora

Date: 2026-08-14  
Task: `M1.2-RESEARCH`  
Scope: research only; no Lingora schema/database implementation

> **Historical research notice (2026-10-28):** This document preserves the unique five-project benchmark conducted against the early 17-model/historical schema baseline. Its comparisons and conclusions are historical research provenance and do not represent current 34-model implementation facts.

## 1. Executive Summary

Five real repositories were inspected at pinned commits. Lingora's logical model is broadly proportionate to its approved scope. The strongest source-backed confirmations are:

- ordered Course/Lesson content and explicit publication state are common and useful;
- a current SRS/card state separated from historical review events is a sound design;
- user-owned progress/message rows need server-derived ownership checks, not trusted client user IDs;
- composite uniqueness is appropriate for translations, ordered children and role assignments;
- JSON/typed payloads are viable for heterogeneous exercises when schema validation is enforced;
- chat messages need an indexed parent/session path plus deterministic ordering.

The research does not justify adding Module/Chapter, attempt-history, generalized RBAC, chat analytics metadata, partitioning, or extra exercise types to M1.2. Those would be possible overengineering for Lingora's current Must scope.

Decision boundary: **READY WITH DECISIONS**. The model is broadly sound, but the first migration should wait for explicit decisions on UserProgress semantics, delete behavior, vocabulary uniqueness, publication validation, ADMIN representation, chat ordering and concrete indexes.

## 4. Relationship Comparison

### SOURCE OBSERVATION

- LibreLingo orders modules and skills by their list position in `course.yaml` and `module.yaml`; a Skill contains words/phrases and generates challenges.
- Frappe LMS links Course Chapter to Course, Course Lesson to Chapter (and also Course), and Course Progress to member/course/chapter/lesson. Its test `tests/security/test_course_progress_idor.py` rejects progress creation for another member and tests rebinding to the session user.
- Chatwoot stores messages with required `conversation_id` and `account_id`; conversations have an account-scoped unique display identifier and messages have indexes beginning with `conversation_id` and `created_at` combinations.
- Supabase user-management examples use `profiles.id` as both primary key and FK to `auth.users.id`.

### INTERPRETATION

- Ordered child content needs either a stable list representation or a parent-scoped order constraint.
- Redundant parent references, as seen in Frappe Lesson linking both Chapter and Course, can ease queries but also permit inconsistency unless validated.
- Session ownership should be checked at the parent; child message authorization can derive through the session relationship.

### LINGORA RECOMMENDATION

- Keep Course → Lesson without Module/Chapter for M1.2 (`POSSIBLE_OVERENGINEERING` if added now).
- Keep unique `(courseId, orderIndex)`, `(lessonId, orderIndex)`, and LessonVocabulary ordering constraints.
- Require ChatMessage to reference ChatSession and choose a deterministic session-local order strategy before migration.

## 5. Constraint / Index Comparison

### SOURCE OBSERVATION

- Supabase Slack clone uses unique `channels.slug`, unique `(user_id, role)`, unique `(role, permission)`, FK `messages.channel_id ... on delete cascade`, and RLS ownership using `auth.uid()`.
- Chatwoot uses unique conversation UUID, unique `(account_id, display_id)`, and multiple query-oriented message indexes including `(conversation_id, account_id, message_type, created_at)`.
- Supabase profile examples use PK/FK identity to `auth.users` and a username length check.
- Frappe's data model and patches include explicit course/lesson/progress link fields and a patch named `delete_duplicate_course_progress.py`, showing duplicate progress was significant enough to require cleanup; this is evidence for enforcing Lingora's approved unique `(userId, lessonId)`.

### INTERPRETATION

- Composite uniqueness should encode domain identity, not merely speed queries.
- Foreign-key columns used for ordered listing, ownership or due-card lookup normally need explicit indexes in PostgreSQL; FKs do not automatically create source-column indexes.
- Cascade can be safe for pure dependent content, but historical/learner data needs a retention decision.

### LINGORA RECOMMENDATION

Review these candidate indexes before migration; they are proposals, not canonical decisions:

- `Lesson(courseId, orderIndex)` unique (already approved logically).
- `Exercise(lessonId, orderIndex)` unique.
- `LessonVocabulary(lessonId, orderIndex)` unique and `(lessonId, vocabularyId)` unique.
- `UserProgress(userId, lessonId)` unique.
- `UserVocabSrs(userId, nextReviewAt)` for due-card queries.
- `ReviewLog(srsCardId, reviewedAt)` and/or `(userId, reviewedAt)` according to authorized query paths.
- `ChatMessage(sessionId, createdAt, id)` or session-local sequence unique/index.
- Translation composite primary/unique keys already approved.

## 6. SRS Comparison

### SOURCE OBSERVATION

- AnkiDroid `Card.kt` and `FlashCardsContract.kt` expose current scheduler state such as queue, due, interval, repetitions, ease factor, last-review time and optional memory-state fields.
- `Collection.getReviewLogs(cardId)` returns review-log entries separately. `Scheduler.kt` queries the `revlog` table to estimate historical rates.
- The contract explicitly says card-level last-review time is stored state and “is not synthesized from the revlog”.

### INTERPRETATION

This is strong evidence for separating mutable current scheduling state from append-oriented historical events. It also demonstrates that current state can include scheduler-specific fields without making history redundant.

### LINGORA RECOMMENDATION

`NO_CHANGE`: retain `UserVocabSrs` as current state and `ReviewLog` as history. Keep `record_review` atomic across both. Do not import Anki-specific queue encodings, FSRS fields or SM-2 internals wholesale; Lingora has DKT/HLR probability plus a separate rule-based Scheduler.

Review whether `ReviewLog` needs response time and model/scheduler version based on actual ML requirements. Do not add them merely because Anki records more metadata.

## 7. Exercise Comparison

### SOURCE OBSERVATION

- LibreLingo defines words/phrases and generates challenge JSON for cards/options/short-input/listening/chips.
- Frappe LMS uses Quiz plus child Question/Result structures and stores submission score, score-out-of and percentage.
- Chatwoot stores extensible JSON/JSONB metadata but applies JSON schema validation in model code.

### INTERPRETATION

- Separate relational subtype tables provide strong field constraints but increase tables and joins.
- A single typed payload is compact and flexible, but database-level JSON shape validation is limited unless checks/functions or application validation are added.

### LINGORA RECOMMENDATION

`NO_CHANGE` to `Exercise(type, payload)` for only MCQ, FILL_BLANK and REORDER. Before migration, approve where validation lives and ensure seed/admin writes cannot bypass it. Do not add Matching/Listening/Writing because sources support them.

## 8. Translation Comparison

### SOURCE OBSERVATION

- LibreLingo explicitly stores the learned language and “For speakers of” language as BCP-47 codes; vocabulary translations are embedded in skill content.
- Lingora already normalizes Course/Lesson/Vocabulary translations with composite entity+locale identity.
- No studied relational project supplied evidence strong enough to prove JSON or translation tables universally superior.

### INTERPRETATION

- Embedded translations are simple for static course packages but make independent querying/editing/fallback harder.
- Translation tables suit Lingora's Admin CRUD and locale fallback, at the cost of more joins and publication validation.

### LINGORA RECOMMENDATION

`NO_CHANGE`: retain normalized translation tables and approved fallback semantics. `REVIEW`: decide the minimum translation row(s) required before publication and whether locale codes are constrained by FK to `Language`.

## 9. Security / RLS Comparison

### SOURCE OBSERVATION

- Supabase user-management migrations create Profile rows keyed to `auth.users`, enable RLS, and use `auth.uid() = id` for own insert/update. A SECURITY DEFINER trigger creates profiles after signup.
- Supabase Slack clone separates `user_roles` and `role_permissions`, uses unique pairs, SECURITY DEFINER authorization helpers with an explicit `search_path`, and ownership policies based on `auth.uid()`.
- Frappe LMS's progress IDOR test verifies that a learner cannot submit progress for another member even when a lower permission layer is bypassed.
- Supabase Storage examples show policies must explicitly bind bucket and owner; one inspected avatar example permits broad upload and is therefore evidence to evaluate critically, not copy for Lingora.

### INTERPRETATION

- RLS should be backed by server/controller invariants for security-sensitive mutations.
- SECURITY DEFINER functions should minimize trust in arguments and set a controlled search path.
- General role/permission tables are flexible but may exceed Lingora's single ADMIN role needs.

### LINGORA RECOMMENDATION

- `NO_CHANGE`: `record_review` derives identity from `auth.uid()`, verifies card ownership, and performs one transaction.
- `REVIEW`: choose ADMIN representation before M1.3. A profile enum/field or claim may be sufficient; do not automatically introduce generalized role/permission tables.
- `REVIEW`: child content policies should authorize through the published/admin-owned parent.
- `NO_CHANGE`: Storage remains Admin-managed; do not copy public or “anyone upload” example policies.

## 11. Recommended Questions Before M1.2 Approval

1. Is `UserProgress.score` a 0–100 percentage, raw correct count, or nullable latest/best score? What exact event sets `COMPLETED`?
2. Which content deletions cascade, which are restricted, and should published/referenced content be archived instead of deleted?
3. Is vocabulary identity unique by `(languageCode, normalizedTerm)`, course, or another approved scope? How is normalization defined?
4. Which translation locales/fields must exist before Course/Lesson/Vocabulary publication, and where is validation enforced?
5. Is `Exercise(type,payload)` validation enforced in Admin/application code, database checks, or both?
6. Confirm `UserVocabSrs` current state + append-only `ReviewLog`; decide whether response time/model/scheduler version is required by ML traceability.
7. How are ChatMessages deterministically ordered within a session: timestamp+UUID or explicit sequence? What deletion/retention applies?
8. Is ADMIN stored in Profile, JWT/app metadata, or a small role table? How are privilege changes propagated safely?
9. Approve concrete indexes for due SRS, ordered content, progress ownership, review history and chat message retrieval.
10. Confirm parent-derived RLS for translations/exercises/messages and controlled SECURITY DEFINER `search_path`/ownership checks.
11. Approve Session Pooler `:5432` and the minimal canonical correction to the outdated connection example.

## Final Assessment

### READY WITH DECISIONS

Lingora's current logical model is good enough as a baseline and does not need architectural redesign. It is not yet safe to produce the first migration because several concrete database semantics and indexes remain intentionally unresolved.
