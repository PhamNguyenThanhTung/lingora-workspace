## Objective

Implement the stateless FastAPI mock runtime for `lingora-ai/api/` according to the canonical contract in `docs/03-api-contract.md` and architecture rules in `docs/01-architecture.md`.

The FastAPI service provides:
1. **Deterministic SRS Schedule Inference Mock (`POST /v1/srs/schedule`):**
   - Calculates stable `recall_probability` via SHA-256 hash of `vocabulary_id`.
   - Computes rule-based `priority` (`REVIEW_NOW`, `REVIEW_TODAY`, `REVIEW_LATER`) and `recommended_interval_days`.
   - Returns metadata: `model_version: "dkt-lstm-v1.0.0"`, `scheduler_version: "rule-v1"`, `is_mock: true`.
2. **Deterministic Roleplay Chat Inference Mock (`POST /v1/chat/roleplay`):**
   - Supports published `hotel_booking` scenario with contextual receptionist replies.
   - Provides optional `grammatical_acceptability_score` and `feedback` format per contract.
   - Returns metadata: `model_version: "chat-t5small-v1.0.0"`, `is_mock: true`.
3. **Scenario & Model Info Lookups:**
   - `GET /v1/chat/scenarios`: Returns published scenarios matching M1.4 seed (`hotel_booking`).
   - `GET /v1/model/info`: Returns model architectures, datasets, and target metrics for documentation/evaluation.
4. **Health & Lifecycle Endpoints:**
   - `GET /health/live`: Liveness probe (HTTP 200 `{"status": "ok"}`).
   - `GET /health/ready`: Readiness probe checking mock/real service readiness (HTTP 200).
5. **Standardized Error Envelope:**
   - Error format `{"error": {"code": "...", "message": "...", "detail": ...}}` for `INVALID_INPUT` (400), `TEXT_TOO_LONG` (413), `LANG_NOT_SUPPORTED` (422), `SCENARIO_NOT_FOUND` (404), and `UNAUTHORIZED` (401).

## Architectural Boundaries & Principles

- **Stateless AI Boundary:** The AI server does **NOT** connect to Supabase PostgreSQL or Storage directly. The client passes review logs and history context in request bodies.
- **`MOCK_MODE=true` Mandatory Baseline:** When `MOCK_MODE=true` (or when weights are not present), endpoints return deterministic mock responses satisfying the exact same JSON schema as real PyTorch models.
- **Contract Conformance:** All JSON fields use `snake_case`, API version is `/v1/`, and Pydantic v2 validates request/response envelopes.

## Test Plan & Acceptance Criteria

1. **Health Probes:**
   - `GET /health/live` returns HTTP 200 with `{"status": "ok"}`.
   - `GET /health/ready` returns HTTP 200 with `{"status": "ok", "srs_ready": true, "nlp_ready": true, "mock_mode": true}`.
2. **SRS Endpoint Contract (`POST /v1/srs/schedule`):**
   - Valid items return HTTP 200 with matching vocabulary IDs, `recall_probability` in `[0.0, 1.0]`, valid `priority` (`REVIEW_NOW` / `REVIEW_TODAY` / `REVIEW_LATER`), `model_version: "dkt-lstm-v1.0.0"`, `is_mock: true`.
   - Repeated calls with the same `vocabulary_id` return the exact same `recall_probability` (deterministic hash).
   - Empty `items` returns HTTP 400 with code `INVALID_INPUT` in standard error envelope.
3. **Chat Roleplay Endpoint Contract (`POST /v1/chat/roleplay`):**
   - Valid `hotel_booking` request returns HTTP 200 with non-empty `ai_reply`, `grammatical_acceptability_score` in `[0.0, 1.0]`, `model_version: "chat-t5small-v1.0.0"`, `is_mock: true`.
   - `user_message` > 500 characters returns HTTP 413 with code `TEXT_TOO_LONG`.
   - `lang != "en"` returns HTTP 422 with code `LANG_NOT_SUPPORTED`.
   - Invalid `scenario_code` returns HTTP 404 with code `SCENARIO_NOT_FOUND`.
4. **Scenarios & Model Info:**
   - `GET /v1/chat/scenarios` returns HTTP 200 list containing `hotel_booking`.
   - `GET /v1/model/info` returns HTTP 200 with details for both DKT-LSTM and T5-small models.
5. **Standard Error Envelope Integrity:**
   - All 4xx errors follow `{"error": {"code": str, "message": str, "detail": object}}`.
6. **Code Quality & Scope Discipline:**
   - 100% pytest suite passes.
   - `git diff --stat` strictly confined to `lingora-ai/api/` and logs/plans.
   - Zero changes to database, schema, migrations, or Android source.
