## Approved `record_review` Security Boundary

Implementation must:

1. Require an authenticated caller and derive the user from `auth.uid()`.
2. Select and lock the requested SRS card only when `user_id = auth.uid()`.
3. Reject a missing or non-owned card before any write.
4. Validate probability and interval inputs against existing database constraints.
5. Insert exactly one ReviewLog and update exactly one UserVocabSrs row in one transaction.
6. Store the previous interval in `ReviewLog.intervalDays`, matching the existing canonical field meaning.
7. Recalculate `next_review_at` server-side from the approved interval and server time.
8. Increment review/lapse counters consistently.
9. Revoke execution from `PUBLIC`/`anon`; grant only the approved authenticated role.
10. Use schema-qualified objects and a fixed safe `search_path` for every security-definer function.
11. Update the vocabulary-review streak atomically using the validated stored IANA timezone.
12. Use row locking for concurrency and do not add an idempotency schema mechanism in M1.3.

## Approved Security Decisions

### SEC-D1 — Auth/Profile bootstrap prerequisite — APPROVED

- The Profile trigger runs in the same transaction as Supabase Auth signup.
- `languages.code = 'vi'` is a required prerequisite because Profile locale defaults are real FKs.
- The trigger does not silently insert general seed data. If `vi` is missing or Profile creation otherwise fails, the Auth signup transaction rolls back.

### SEC-D2 — Profile creation and synchronization — APPROVED

- Auth identity/email is authoritative. Profile creation and verified email synchronization use a trusted synchronous `SECURITY DEFINER` trigger/workflow, not an asynchronous repair process.
- Raw metadata may populate only approved non-privileged profile presentation data after validation. It may never set `role`, identity, streak, audit or other server-controlled fields.
- Trigger/workflow failure is atomic with the relevant Auth write; no partially synchronized Auth/Profile state is accepted.

### SEC-D3 — Profile safe-field update list — APPROVED

- Learner-editable fields are limited to `displayName`, `avatarUrl`, `uiLocale`, `nativeLangCode`, `dailyGoalMin`, and `timezone`, enforced with operation/column-level controls rather than a broad `FOR ALL` policy.
- `id`, `email`, `role`, `streakCount`, `lastQualifyingActivityDate`, and `createdAt` remain server-controlled.
- `dailyGoalMin` requires server/database validation consistent with the existing positive-range database constraint; client validation alone is insufficient.
- Locale FKs and timezone validation must pass before an update is accepted.

### SEC-D4 — Auth user/Profile deletion workflow — APPROVED/DEFERRED

- End-user account deletion is not implemented in M1.3.
- No normal client/content deletion may cascade through learner history.
- Right-to-erasure/account deletion is recorded as explicit technical debt requiring a separately approved privileged workflow covering Auth, Profile and dependent learner data.

### SEC-D5 — Exact learner write paths — APPROVED

- RLS policies are operation-specific; no broad own-row `FOR ALL` policy is permitted.
- `UserProgress` is owner-readable, while result mutation remains a trusted-flow boundary rather than unrestricted direct client writes.
- Chat access derives through the owned ChatSession. `ChatMessage.sequenceNumber` is allocated server-side; clients may not supply or control it.
- Client writes may not forge AI-role messages, transfer ownership, or directly update server-controlled ordering fields. Any session/message delete path must preserve the approved owner and cascade boundary.

### SEC-D6 — ADMIN support visibility and role workflow — APPROVED

- ADMIN content/scenario/media authority does not grant learner-data support access in M1.3. ADMIN cannot read learner Profile/Progress/SRS/Review/Chat rows merely because of the ADMIN role.
- First-ADMIN bootstrap and later role changes use only a privileged trusted/service-role workflow; learner clients cannot self-promote.
- A future audited support/analytics access path is backlog work and requires a separate requirement, audit model and approval. No generalized RBAC is introduced.

### SEC-D7 — Content child visibility predicates — APPROVED

- Learner content visibility follows the published `Course → Lesson` parent chain.
- Lesson translations, Exercise and LessonVocabulary inherit visibility through that chain; Vocabulary/translation reads are limited to vocabulary reachable from visible published learning content.
- Draft/unpublished parent content remains hidden from learners; ADMIN retains the approved content-management boundary.
- Do not denormalize publication/visibility flags without measured performance evidence and a separately approved design change.

### SEC-D8 — Storage contract — APPROVED WITH PRE-IMPLEMENTATION CONTRACT CHECK

- Content media uses private Supabase Storage and learner delivery uses signed URLs; anonymous/public bucket delivery is not approved.
- Upload/replace/delete remains ADMIN-controlled. Signed URLs are generated only by a trusted server/service-role generator; learners cannot generate arbitrary object access or choose TTL.
- Before implementation, the reviewed Storage contract must record the signed-URL owner/generator, centrally controlled finite TTL, stable bucket/path rules, allowed MIME types, maximum sizes, overwrite/delete behavior and attachment-to-visible-content check.
- The exact TTL is an operational contract value, not client-supplied. It must be recorded and reviewed before policy/function SQL is created.
- Vocabulary audio is in scope. Profile avatar ownership remains limited to the approved Profile safe-field/Storage contract and must not weaken content-media policies.

### SEC-D9 — `record_review` signature, streak and timezone — APPROVED

- The canonical M1.3 RPC signature excludes `p_response_ms`; no `response_ms` column or other ML provenance field is added.
- A valid owned review atomically inserts ReviewLog, updates UserVocabSrs and applies the approved vocabulary-review streak transition.
- `Profile.timezone` is learner-editable only when it validates as an IANA timezone. Streak day calculation uses that validated stored timezone and server time.
- Missing/non-owned cards or invalid inputs fail before any ReviewLog, SRS or Profile mutation.

### SEC-D10 — RPC retry/concurrency behavior — APPROVED AS AMENDED

- M1.3 uses row locking to serialize concurrent updates and prevent lost counters/schedule state.
- M1.3 adds no idempotency table, column, token or schema mechanism.
- An ambiguous client timeout after submission is a known limitation: the client must not automatically retry when commit outcome is unknown.
- Client retry is permitted only after a clearly confirmed failure indicating the transaction did not commit.
- End-to-end idempotency is placed in the M1.4+ backlog and requires a separate schema/API decision before implementation.

## Acceptance Criteria

- Every application table has an explicit reviewed RLS/grant posture; no table relies on accidental defaults.
- Auth creation cannot produce a missing, privileged or cross-user Profile.
- Learners cannot self-promote or mutate server-controlled Profile fields.
- Learner-owned rows are isolated across two independent test users.
- ADMIN permissions are limited to the approved content/support boundary.
- Storage behavior exactly matches approved bucket/path/type/size/visibility rules.
- `record_review` authenticates via `auth.uid()`, rejects non-owner calls before writes, and atomically writes the approved state.
- Direct client mutation of `UserVocabSrs` and `ReviewLog` is denied.
- No unapproved schema field/table, seed, application feature, ML/NLP work or dependency is introduced.
- All security tests and logs contain reproducible evidence without credentials.

## Risks

- The `vi` locale FK can make the Auth trigger fail before deterministic seed exists.
- Self-referencing Profile role checks can cause RLS recursion if implemented naively.
- Broad `FOR ALL` policies or missing `WITH CHECK` clauses can permit ownership transfer or privilege escalation.
- Security-definer functions without a fixed `search_path` or restricted execute grants can be exploited.
- Child-content policies can leak draft content if they do not validate the full published parent chain.
- Storage contract values must be frozen before policy/function SQL; a missing generator/TTL/path/type/size rule stops implementation review.
- Legacy `p_response_ms` wording must not leak into the M1.3 RPC because the approved signature excludes it.
- Row locking prevents lost concurrent updates but does not make ambiguous timeout retries idempotent; this is an accepted M1.3 limitation and M1.4+ technical-debt item.
- Deferred account deletion leaves a documented right-to-erasure technical-debt obligation.
- Test cleanup must not use broad destructive commands or affect non-test Supabase data.
